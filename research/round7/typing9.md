## F750 (medium, regression): Wikipedia portal search shows no suggestions through Sift

Found by: T3-tools. Where: https://www.wikipedia.org/ ('Search Wikipedia' field)

Evidence: With Sift on, I typed 'Pumper', 'Baguette' and 'Bagu' at 20 and at 200 ms/key. Sift showed 0 suggestions in 4 of 4 runs, with low machine load too (load average 1.3). The page field held the value ('Pumper'), but the page never created its .suggestions-dropdown. With Sift off, a real click in #searchInput and typing 'Pumper' made .suggestions-dropdown (427 px) with 6 suggestion links. Enter still works through Sift ('Bagu' opened /wiki/Bagu). Listeners on #searchInput are keydown, focus and input. works.md line 247 says the portal's article search shows suggestions. Shots: /home/nico/projects/sift-test-3/research/shots/R7-T3-wiki-portal-sift.png (Sift) and /home/nico/projects/sift-test-3/research/shots/R7-T3-wiki-portal-orig.png (original).

Repro: cd /home/nico/projects/sift-test-3; export SIFT_PORT=9463 SIFT_TAB=T3-tools; bun scripts/act.ts goto:https://www.wikipedia.org/ wait:7000 "type:input[type=search]=>Pumper" wait:5000 "eval:document.querySelector('sift-root').shadowRoot.querySelectorAll('.sheet a, .sheet button, .suggest a, .suggest button').length+' / page dropdowns '+document.querySelectorAll('.suggestions-dropdown').length+' / page value '+document.querySelector('#searchInput').value"  (prints '0 / page dropdowns 0 / page value Pumper'). Control: press Alt+Shift+S, real-click #searchInput and type 'Pumper' to get 6 suggestions.

Suspected cause: The portal's typeahead probably builds its dropdown on the field's 'focus' event. Sift keeps the page inert and replays only input, so focus never reaches the page field. Lead: send a focus event to the page field when the user enters Sift's field.

Skeptic: Reproduced 2 of 2 with Sift on, typing 'Pumper' and 'Baguette' into Sift's 'Search Wikipedia' field on www.wikipedia.org. Sift showed 0 suggestions and the page made no .suggestions-dropdown, even though the page field held the value. The page's JSONP query did fire (#api_opensearch script present). The control with Sift off (real click in #searchInput, type 'Pumper') gave a 427 px dropdown with 6 links. The suspected cause is wrong. The portal's focus and input listeners are the same 100 ms debounced query, and its render callback (portalOpensearchCallback) draws only `if (document.activeElement === searchInput)`. With Sift on, document.activeElement is sift-root. Sift's activeElement shim in src/main/index.ts only applies after a 'sift-enter', and proxy.focus() sends that only for fields matching [role=combobox], [aria-autocomplete], [aria-controls], [aria-owns] or [list]. The portal's #searchInput has none of these (type=search, autocomplete=off). works.md line 247 says this worked in round 6, so the regression claim is consistent.

Skeptic's fix lead: In src/content/proxy.ts focus(), also send 'sift-enter' for plain search fields (input[type=search], [role=searchbox], or a text input inside a search form or role=search), so the activeElement shim in src/main/index.ts names the page field. Alternatively, apply the shim to any text field Sift has entered.

## F751 (medium): Wikipedia header search: under machine load the suggestion list often never appears after quick typing

Found by: T3-tools. Where: https://en.wikipedia.org/wiki/Bagel, /wiki/Rye_bread, /wiki/Croissant, /wiki/Brioche ('Search Wikipedia' in Sift's top bar)

Evidence: While other agents were loading the machine, act.ts typing at 20 ms/key ('focacc', 'focaccia', 'pumpernick', 'brioch', 'ciabat') left Sift's sheet empty in 8 of 16 trials. In each failure the page's #searchform menu held 11 options (aria-expanded=true). The sheet stayed empty 3-11 s later, ArrowDown did nothing, and one more key ('i') made all 11 appear. A paste-like insert (CDP insertText 'focaccia') failed 1 of 3 times. Under low load (load average about 1) the same commands passed 10 of 10, and typing at 60-150 ms/key passed 8 of 8. Round 6's F661 repro used the same act.ts typing and showed the list 3 of 3. Shot: /home/nico/projects/sift-test-3/research/shots/R7-T3-wiki-nosuggest.png

Repro: cd /home/nico/projects/sift-test-3; export SIFT_PORT=9463 SIFT_TAB=T3-tools; for p in Bagel Rye_bread Bagel Rye_bread Croissant Brioche; do bun scripts/act.ts goto:https://en.wikipedia.org/wiki/$p wait:7000 "type:header input=>focacc" wait:3000 "eval:document.querySelector('sift-root').shadowRoot.querySelectorAll('.sheet button').length+'/'+document.querySelectorAll('#searchform .cdx-menu-item').length" wait:8000 "eval:document.querySelector('sift-root').shadowRoot.querySelectorAll('.sheet button').length"; done  (a failure prints '0/11', then 0). It only shows while the machine is busy; run it while other test Chromes are loading pages.

Suspected cause: After the last keystroke, Sift extracts once before the page's list fills (or skips the run). No later mutation brings the sheet up until another input event. Possibly the new suggestAt fast path in index.ts's mutation observer, or the typedRun timer: schedule(...lastRunAt + max(100, lastDur*2) - now).

Skeptic: Reproduced as a lasting sync failure. Unthrottled at low load it passed 4 of 4. Unthrottled at load average 12-22 it failed 1 of 4 and 1 of 1. With renderer CPU throttling via CDP Emulation.setCPUThrottlingRate, which simulates a slower machine, it failed 3 of 3 at 2x, 2 of 2 at 3x, 3 of 3 at 4x and 4 of 5 at 6x. In every failure the page's #searchform menu held 11 options with aria-expanded=true and the value typed. Sift's sheet stayed at 0 buttons at 3, 8 and 18 s, and still 5 s after throttling was removed. host.dataset.runs shows Sift ran an extraction after the list filled (6 to 7), so runs happened but produced no sheet. In the slow runs the page had not yet swapped #searchInput for the Codex typeahead input when typing ended: at 3 s the input was still searchInput with no aria-controls; later it was an input with aria-controls=v-0. document.activeElement stayed sift-root, so no sift-enter took effect. This points to Sift's ref still naming the old, removed field. fieldList() uses elOf(a.dataset.ref), which returns null for a disconnected element, so it returns undefined. Only the next keystroke adopts the new field, via input() calling liveField(), which matches the report that one more key shows the list.

Skeptic's fix lead: In src/content/index.ts fieldList(), resolve the page field with liveField(a.dataset.ref, false) instead of elOf(), so a swapped-in field (Wikipedia's typeahead) is adopted at the next run. Also, in the 'sift-focus' handler, adopt the new field even when the old one is still connected at the moment of the page's focus() call. Then send proxy.focus/sift-enter to the adopted field.

## F766 (high, regression): While typing in a field with suggestions, every page change re-extracts the whole page about every 2 x lastDur, and on long pages typing stalls for seconds

Found by: R2-interaction. Where: src/content/index.ts:2110 (schedule with the suggestAt fast path), src/content/index.ts:2794 (suggestAt set on every keystroke)

Evidence: Wikipedia /wiki/United_States, Sift's 'Search Wikipedia' field, 25 characters at 120 ms per key, with a long-task observer. I compared the current build with a control build where only line 2110 is replaced by schedule(undefined, minor). The runs alternated in time on the same machine, which was loaded (load average 10 to 13 on 6 cores). Current build, 2 runs: 3 and 4 full extractions during typing (lastDur about 1.1 s); slowest key-to-handled time 3097 and 3171 ms; typing took 9.0 and 8.5 s. Control, 2 runs: 1 and 2 extractions; slowest key 115 and 100 ms; typing took 4.3 and 3.8 s. /wiki/Bagel: 11 extractions during typing against 2, long tasks 4.4 s against 2.1 s, p90 key time 440 ms against 135 ms. The original page with Sift off: slowest key 9 ms, no long tasks.

Repro: SIFT_PORT=9467 SIFT_TAB=R2-interaction bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r7int/typelag.ts https://en.wikipedia.org/wiki/United_States (add the argument 'orig' to type in the original). The control build is in /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/ctl (index.ts:2110 changed; it was run on port 9477, now stopped).

Suspected cause: The genb7 F637 fix replaces the idle back-off (at least lastDur x 9, capped at 8 s, on big pages) with a full extraction every max(100, 2 x lastDur) ms for 4 s after each key. On a page where one extraction takes about a second, that keeps the main thread busy while the user types. Refreshing only the suggestion list (fieldList or the popup) or capping by lastDur would avoid it.

Skeptic: Reproduced on Wikipedia /wiki/United_States with 25 characters typed into Sift's search field. I alternated the current build (port 9467) with the reporter's control build, which differs only at index.ts:2110; I checked that in the built content.js. The machine was very loaded (load average 17 to 38 on 6 cores), so the absolute times are inflated. The pattern held on every run. Current build, 3 runs: slowest key 2913, 2935 and 4706 ms; typing took 6.7, 7.5 and 10.0 s; long tasks totaled 7.0, 6.0 and 10.2 s. Control, 2 runs: slowest key 115 and 146 ms; typing took 3.8 and 4.4 s; long tasks totaled 2.2 and 2.8 s. The control's 1 or 2 runs fall mostly after typing stops, at the 300 ms typedRun. Original with Sift off: slowest key 79 ms. The code matches the claim. For 4 s after each key, every page change schedules a full run at lastRunAt (the run's start) + 2 x lastDur. That keeps the main thread busy about half the time while the user types on a big page. Without this path, schedule() waits at least lastDur x 9, up to 8 s, in idle time. On an unloaded machine the stalls would be shorter, but they still scale with lastDur. This regression goes against 'must feel fast'.

Skeptic's fix lead: In src/content/index.ts at line 2110, use the suggestion fast path only on cheap pages (for example lastDur < ~150 ms). Otherwise, space runs by at least lastDur x 6, or refresh only the suggestion list (the field's list or popup) instead of running a full extraction.
