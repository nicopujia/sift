## F923 (high): Test harness: the test Chrome ran an old service worker (PROMPT_VERSION 8) while content.js was the merged build

Found by: T2-news. Where: scripts/chrome.sh start / scripts/launch.ts on the existing profile /home/nico/projects/sift-test-2/.chrome/profile (port 9462)

Evidence: After 'SIFT_PORT=9462 ./scripts/chrome.sh start', I compared the running service worker's background.js with dist/background.js via CDP Debugger.getScriptSource. It was 47675 chars with 'PROMPT_VERSION = 8' and no stableContext. dist/background.js on disk was 62352 chars with 'PROMPT_VERSION = 10'. The content script was new (F823's Search and Sign In buttons were there). So every AI line and Short version came from old code and old cache keys. For example, the misattributed Maradona line from 18:26 was still served. chrome.runtime.reload() left the extension blocked (ERR_BLOCKED_BY_CLIENT). 'chrome.sh reload' (uninstall + install) loaded v10 but wiped the IndexedDB cache. All my AI checks were made after that reload. Other testers' Chromes (9461, 9463, 9464, 9467) may have the same problem, and it may explain round 8's unexplained F725 lines.

Repro: cd /home/nico/projects/sift-test-2; SIFT_PORT=9462 ./scripts/chrome.sh start; SIFT_PORT=9462 bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9t2/swdump.ts; grep -o 'PROMPT_VERSION = [0-9]*' /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9t2/bg-running.js /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9t2/bg-disk.js (the 'running' file shows the service worker's code, the 'disk' file shows dist/). This was the state before my reload; after 'chrome.sh reload' both are 10.

Suspected cause: installExtension (Extensions.loadUnpacked) on a profile that already has the same unpacked extension and the same manifest version keeps the cached service worker script. Content scripts are read again, the service worker is not. Fix lead: bump the manifest version per build, or uninstall before install in launch.ts. Tell testers to run 'chrome.sh reload' once after start and verify with swdump.

Skeptic: Reproduced. This is a bug in the test harness, not in what users get. I ran a separate experiment with its own profile in /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/skep/n0.ts and n0b.ts, doing what launch.ts does: launch puppeteer on an existing profile, then installExtension. I changed a marker in background.js between launches. Launch 1 ran MARK_A. Launches 2 and 3 still ran MARK_A while the disk had B and C. The content script did change (MARK_B), so a run mixes a new content script with an old service worker. Uninstall + install (the chrome.sh reload path) ran the new code (MARK_D). The tester's fix lead does not work. With the manifest version bumped to 9.9.9.1, .2 and .3, Chrome reported the new version from getManifest(), but the service worker was still MARK_A (n0c.ts). Deleting <profile>/Default/Service Worker/ScriptCache made the next launch fail to start the service worker. The launch after that ran the new code, and IndexedDB was kept. I could not check the tester's past state (v8 at 47675 chars). Right now 9462 runs v10, the same as dist. Several other testers' Chromes (9463, 9472, 9473) are running and may be affected.

Skeptic's fix lead: scripts/launch.ts: after the first installExtension, do what the SIGUSR1 handler does, uninstallExtension(id) then installExtension(dist). Or have chrome.sh start always end with a reload and print the running service worker's PROMPT_VERSION. Do not rely on a manifest version bump: tested, it does not refresh the service worker. Note that the uninstall wipes the IndexedDB cache.
