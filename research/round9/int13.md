## F950 (high, regression): Sift's bar Search button no longer sends the field's change and blur before clicking the page's button, so a search without a form runs with the old query

Found by: R2-interaction. Where: src/content/index.ts:774 (mousedown on 'form.search button[type=submit]' is cancelled, F856) with src/content/proxy.ts:598 (no-form search with via 'button': click(button) without finishEditing)

Evidence: Fixture fx/r9int-searchchange.html is a bar search with no <form>. Its query is kept on the field's change event, as a value binding does, and its Search button reads it. Mouse: type 'bread' in Sift's bar field, click Sift's Search. Current build: page log ['search ""'], results 'Type something to search.'. Original (Sift off, same mouse flow): ['change bread','blur','search "bread"'], 'Results for bread…'. Pre-round-8 build (sift-r8-base on port 9477): ['change bread','blur','search "bread"'], same results as the original. Before, mousedown moved focus off Sift's field, so H.leave sent change and blur first. Now focus stays, and proxy.submit's no-form button path only clicks the page button.

Repro: Start the test Chrome. Run SIFT_PORT=9467 SIFT_TAB=R2-interaction bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9int/searchchange.ts. It prints SIFT {"log":["search \"\""]…}. Add 'orig' as the first argument for the original. By hand: open http://127.0.0.1:8799/fx/r9int-searchchange.html, type 'bread' in Sift's top search field, and click Sift's Search button with the mouse.

Suspected cause: F856 keeps focus in the field to stop Discourse's blur, but the field's edit then never ends. In proxy.submit's no-form branch, finishEditing(field) (change) should run before click(button), as the blur did before.

Skeptic: Reproduced twice on the current build (port 9467) with fx/r9int-searchchange.html. I typed 'bread' in Sift's bar field and clicked Sift's Search with the mouse. Page log: ['search ""'], results 'Type something to search.' Original (Sift off, same mouse flow): ['change bread','blur','search "bread"'] and 'Results for bread…'. The pre-round-8 build (scratchpad/pre8, which is sift-r8-base's src, on 9477) gave the same as the original in 2 of 2 runs, so this is a regression. In the code, index.ts ~774 cancels mousedown on 'form.search button[type=submit]' while focus is in that form's field (F856), so focus never leaves the field and H.leave never sends change and blur. proxy.submit's no-form branch with via 'button' then runs only `else if (button) click(button)`, with no finishEditing. The form branch and the Enter branch both call finishEditing, so only the mouse button path on searches without a form is hit. That limits the scope to pages that commit the query on change or blur (Knockout value bindings, v-model.lazy). On those pages it is a real wrong-result search. I would call it medium to high.

Skeptic's fix lead: src/content/proxy.ts submit(), no-form branch: call finishEditing(field) before click(button) when field is set (`else if (button) { if (field) finishEditing(field); click(button); }`). Or in index.ts H.submit, flush the field's change (and a blur if wanted) before proxy.submit when F856's mousedown kept focus in the field.

## F951 (high, regression): Escape on a popup the page keeps open hides Sift's copy for good: a calendar under a read-only date field can then never be reached in Sift

Found by: R2-interaction. Where: src/content/index.ts:995-1005 (escapeList: hidden(true) dismisses the list even when the page still shows it) and src/content/index.ts:3185-3190 (only H.input on the same field clears that dismissal)

Evidence: Fixture fx/r9int-pickesc.html: a read-only 'Day' field opens a calendar on focus and click. The calendar ignores Escape and closes on a pick or an outside press. Current build: the click shows Sift's sheet with 27-31. After Escape, the sheet is gone while the page calendar is still open. Tab goes to 'Book'. Shift+Tab back, a click on the field, and ArrowDown all leave the sheet 'none'. The field is read-only, so no typing can bring it back, and the day cannot be picked in Sift. Pre-round-8 build: the sheet stays after Escape, Tab reaches button 27, and ArrowDown focuses 27. On the original, the calendar stays open after Escape and Tab reaches its days.

Repro: SIFT_PORT=9467 SIFT_TAB=R2-interaction bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9int/pickesc.ts prints siftSheet 'none' after Escape, Tab, Shift+Tab, click and ArrowDown, while pageCal stays true. With the pre-round-8 build (port 9477) every line shows 'sheet suggest:27,28,29,30,31'.

Suspected cause: The F853 fix forces the dismissal at setTimeout 0 for any anchored list, and only typing undoes it. Force it only for the plain-search panels F853 was about ('fp:' lists), or also clear the dismissal when the user enters or clicks the field again (H.focus, H.fieldClick).

Skeptic: Reproduced twice on the current build with fx/r9int-pickesc.html. Clicking the read-only Day field shows Sift's sheet with 27-31. After Escape the sheet is 'none' while the page calendar stays open. Tab goes to 'Book'. Shift+Tab back, another click on the field, and ArrowDown all leave the sheet 'none'. In an extra run I clicked Sift's heading and then the field again, and still nothing came back after 7 s: the page calendar never closes (Sift's own presses do not reach the page's outside-mousedown handler), so the dismissal is never lifted. The field is read-only, so the only lift (typing, in H.input via escapedList) cannot happen. The day cannot be picked in Sift. Original: after Escape the calendar stays open, Tab reaches '27', and Enter picks 'Oct 27'. The pre-round-8 build keeps the sheet after Escape, Tab reaches 27, and ArrowDown focuses 27. In the code, escapeList's `setTimeout(() => hidden(true), 0)` (index.ts ~995-1005, the F853 change) forces the dismissal for any list the page still shows. Pre8's hidden() returned early whenever the list was still visible. This is a regression, but only for pickers that ignore Escape. jQuery UI and Bootstrap pickers close on Escape, so they are not affected. Medium to high.

Skeptic's fix lead: src/content/index.ts escapeList: force the dismissal (hidden(true)) only for plain-search panels (fieldPanel 'fp:' / fieldList 'fl:' keys, the F853 case). And/or in H.focus and H.fieldClick, when escapedList?.ref === ref, delete escapedList.key from store.dismissed and dismissedRefs, as H.input already does, so pressing the field again brings the page's still-open popup back.

## F952 (high): After a message is sent, the page's fresh message field gets the sent text again, and a second Enter sends it twice

Found by: R2-interaction. Where: src/content/index.ts:3082 (sift-focus listener calls liveField(refOf(pageFocus)) with sync on) and src/content/index.ts:2864 (proxy.setValue(now, mine.value))

Evidence: Fixture fx/r9int-resend.html is a chat form. On submit it posts the text, replaces the input name=message with a fresh empty one in the same place, and focuses it, as a keyed composer or an HTMX swap with autofocus does. Sift: type 'hello team', press Enter. Sent ['hello team'], but the page field and Sift's field both hold 'hello team'. A second Enter gives sent ['hello team','hello team']. Original: after Enter the page field is '' and the second Enter sends nothing. A page-side trace shows change@old, then focus@new and input@new='hello team' within 9 ms. That is liveField adopting the fresh field on the page's focus() and copying Sift's stale text into it. The pre-round-8 build does the same.

Repro: SIFT_PORT=9467 SIFT_TAB=R2-interaction bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9int/resend.ts. Add 'orig' as the first argument for the original. resend2.ts in the same folder prints the event trace.

Suspected cause: liveField's sync copies Sift's field value into the adopted field even right after an action. carry() already guards this with lastTyped > store.actAt, and the sift-focus path should use the same guard (or sync=false).

Skeptic: Reproduced twice on the current build with fx/r9int-resend.html. I typed 'hello team' and pressed Enter. Result: sent ['hello team'], but the page's fresh field and Sift's field both hold 'hello team'. A second Enter gives sent ['hello team','hello team']. Original: after Enter the page field is '' and the second Enter sends nothing. The pre-round-8 build does the same as the current one, so this is not a regression. In the code, the 'sift-focus' listener (index.ts ~3082) calls liveField(refOf(pageFocus)) with the default sync=true when the page focuses the field it swapped in. liveField then runs proxy.setValue(now, mine.value) (~2864), which copies Sift's stale text into the page's new empty field. carry() has a lastTyped > store.actAt guard against exactly this, and this path does not. It only hits pages that replace the composer element after a send and focus the new one (keyed remount, HTMX outerHTML with autofocus). When it does, it leads to duplicate sends or old text stuck in the field. High is fair.

Skeptic's fix lead: src/content/index.ts sift-focus listener: call liveField(refOf(pageFocus), false) there, or in liveField only sync when lastTyped(mine) > store.actAt, the same guard carry() uses. Then Sift's field takes the page's new (empty) value on the next render.

## F953 (high): When the page redraws the cart row being edited, Sift moves focus to the first field with the same label, so the next key changes another item's quantity

Found by: R2-interaction. Where: src/content/index.ts:302-303 (twinOf falls back to the first control with the same label), used by refocusNow at src/content/index.ts:352-353. The page's own focus on the redrawn field is ignored at src/content/index.ts:3088 because no action was recent.

Evidence: Fixture fx/r9int-cartrow.html has 3 rows, each labelled 'Quantity' with name=qty, as in Shopify's Dawn cart. After a quantity is saved, the page redraws that row and focuses its new field. In Sift: click the 2nd Quantity (Seeded rye), type '1', wait 1.5 s, type '2'. Result: rows [row-a:21, row-b:11, row-c:1], log ['b=11','a=21'], and focus ends on Rye loaf's Quantity. Original: [row-a:1, row-b:211, row-c:1], log ['b=11','b=211']: only Seeded rye changes. With per-item labels (?v=named), Sift matches the original. The pre-round-8 build is worse ('a=11','a=211'). Round 8 removed the text carry (F851) but kept the label-only focus.

Repro: SIFT_PORT=9467 SIFT_TAB=R2-interaction bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9int/cartrow.ts. Add 'orig' as the first argument for the original, or append '?v=named' as the second argument for the control.

Suspected cause: With several Sift controls sharing the label, twinOf takes the first. It should prefer the same rank among same-label controls, or follow the page's own focus() into the redrawn same-kind field while the user is typing (allow pageFocusTo when typedAt is recent).

Skeptic: Reproduced twice on the current build with fx/r9int-cartrow.html. I clicked the 2nd 'Quantity' (Seeded rye), typed '1', waited 1.5 s, then typed '2'. Result: rows [row-a:21, row-b:11, row-c:1], log ['b=11','a=21'], and Sift's focus ends on Rye loaf's Quantity (value 21). Original: [row-a:1, row-b:211, row-c:1], log ['b=11','b=211']. With ?v=named (per-item labels), Sift matches the original. The pre-round-8 build is worse: ['b=11','a=11','a=211']. Not a regression. The cause is in index.ts. liveField cannot adopt the redrawn field: the nearest connected container (#rows) holds 3 qty fields, so `place.n[i] !== 1 && i > 0` returns null. The page's own focus() on the new field is ignored because no action was recent (the check at ~3088). refocusNow then calls twinOf, which falls back to `all.find(c => labelOf(c) === spot.label)`, the first 'Quantity'. Dawn-style carts label every row 'Quantity' and refocus the redrawn row, so the next key or ArrowUp changes the wrong item's quantity. High.

Skeptic's fix lead: src/content/index.ts: record in spotOf the spot's rank among Sift controls with the same tag and label, and in twinOf pick the same-label control at that rank (fall back to the first only when there is a single one). Or, in the sift-focus listener, follow the page's focus() into a same-kind field when typedAt is recent (treat recent typing like a recent action), so focus goes to Sift's copy of the field the page focused.

## F954 (medium, regression): Waking embeds scrolls the hidden original far enough to fire its 'next story' loader, and Sift then shows that story appended

Found by: R2-interaction. Where: src/content/index.ts:1768-1776 (wakeEmbeds: el.scrollIntoView on the hidden original, up to 3 s per embed)

Evidence: Fixture fx/r9int-nextart.html is an article with a blockquote.twitter-tweet near its end. Its widget never renders, as on a page with consent not given. Below the article, an IntersectionObserver (rootMargin 800px) loads the next story. Current build: about 1.7 s after load the page log shows 'first scroll' and 'next story loaded'. Sift's main view then contains the next story's text ('coastal road'), and the reader never scrolled there. Pre-round-8 build: log [], no next story. On La Nación (F830's URL) the original was scrolled to y=2882 twice, at 6.4 s and 19.4 s, each time for about 6 s.

Repro: SIFT_PORT=9467 SIFT_TAB=R2-interaction bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9int/nextart.ts prints log ['first scroll…','next story loaded…']. Then bun scripts/act.ts "eval:document.querySelector('sift-root').shadowRoot.querySelector('#sift-main').textContent.includes('coastal road')" prints true. With the pre-round-8 build (port 9477), the log is [].

Suspected cause: scrollIntoView({block:'center'}) shows the whole viewport around the embed in the original, so any scroll-linked loader near it fires too. Bring only the embed into view (block 'nearest' near the viewport's top edge), or skip waking when the scroll would reach the page's end.

Skeptic: Reproduced twice on the current build with fx/r9int-nextart.html. About 1.7 s after load the page log shows ['first scroll at ~1700','next story loaded at ~1700']. Sift's #sift-main then contains the next story's text ('coastal road' is true; its paragraphs are appended at the end of Sift's view), though the reader never got near the end. The original's scroll is restored afterward (docY 0). The pre-round-8 build: log [] and 'coastal road' false, so this is a regression from the F830 change. In the code, wakeEmbeds (index.ts ~1751-1777) calls el.scrollIntoView({block:'center'}) on the hidden original for each embed quote and holds it there up to 3 s. Any scroll-linked loader near the embed fires (next-story loaders, lazy comments, read tracking). I did not check La Nación live; the evidence is the fixture plus the code. One caution on the reporter's fix: block 'nearest' or 'start' would not help here, because with an 800 px rootMargin the sentinel right after the embed still intersects. Medium is fair.

Skeptic's fix lead: src/content/index.ts wakeEmbeds: skip (or defer until the reader scrolls near it in Sift) any embed whose wake scroll would bring the viewport within about a screen plus a margin of the document's end (el's bottom + scrollY + innerHeight + ~1000 > scrollHeight). Or watch for large content appended outside the embed during the wake, and stop waking when that happens. Changing only the scrollIntoView block option is not enough.
