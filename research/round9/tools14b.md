## F962 (medium): MDN compatibility table: only 4 of 13 browser columns fit, the rest are hidden in a sideways scroll

Found by: T3-tools. Where: https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share (Browser compatibility); the same on every MDN compat table

Evidence: Sift's compat table is 1592 px wide inside a 756 px .table-wrap (overflow-x:auto). The fully visible headers are Chrome, Edge, Firefox and Opera. Safari, Chrome Android, Firefox for Android, Opera Android, Safari on iOS, Samsung Browser, WebView Android, WebView on iOS and Node.js sit off to the right. The only sign of them is a cut 'S' header and cut cell buttons at the box's right edge. In the test Chrome the box draws no scrollbar (offsetHeight 567 = clientHeight 567). I could not check whether a desktop Chrome with classic scrollbars draws one. The original (Sift off, 1280 px) fits all 13 columns in a 689 px table (scrollWidth 689). Safari and mobile support, a main reason to open the table, is out of sight. Shots: /home/nico/projects/sift-test-3/research/shots/R9-T3-mdn-compat-sift-wrap.png, /home/nico/projects/sift-test-3/research/shots/R9-T3-mdn-compat-orig.png

Repro: cd /home/nico/projects/sift-test-3; export SIFT_PORT=9463 SIFT_TAB=T3-tools; bun scripts/act.ts goto:https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share wait:9000 "eval:(()=>{const r=document.querySelector('sift-root').shadowRoot;const w=[...r.querySelectorAll('main .table-wrap')].pop();const wb=w.getBoundingClientRect();const vis=[...w.querySelectorAll('th')].filter(th=>{const b=th.getBoundingClientRect();return b.left>=wb.left-1&&b.right<=wb.right+1}).map(th=>th.innerText.trim()).filter(Boolean);return 'sw='+w.scrollWidth+' cw='+w.clientWidth+' visible: '+vis.join(',')})()"  (prints sw=1592 cw=756 visible: Chrome,Edge,Firefox,Opera)

Suspected cause: Sift renders the compat cells as wide text buttons ('128 (Has more compatibility info)'), not MDN's condensed icon columns, so the table cannot fit Sift's 756 px column.

Skeptic: Reproduced on Navigator.share at 1280 px. Sift's compat .table-wrap had scrollWidth 1487 and clientWidth 756. Only Chrome, Edge, Firefox, Opera and Safari were fully visible (5 of 13; the count varies a little by load, and T3 saw 4). Chrome Android and the other mobile/Node columns sit to the right; the cut 'Chrom Andro' header is the only sign of them. Cells are wide text buttons like '128 (Has more compatibility info)' and '71 (No support, User must explicitly enable this feature)'. Original with Sift off: all 16 header cells fit in a 689 px table (parent scrollWidth = clientWidth = 689). A second page, <dialog>, showed 8 of 12 columns (sw 1148). So the effect is general, though smaller on tables with fewer notes. One correction: 'the box draws no scrollbar' is a harness artifact, because launch.ts starts Chrome with --hide-scrollbars. Real Chrome on Windows or Linux draws one; macOS overlay scrollbars hide it until scrolled. The core problem still stands: Safari/mobile support is off screen where the original shows it at a glance. Medium is fair.

Skeptic's fix lead: src/content/extract/generic.ts table-cell extraction: when a cell's control text is a short value plus visually-hidden notes ('128' + 'Has more compatibility info'), show the short value and move the notes to aria-label/title. Or in src/content/ui/app.tsx (the case "table" renderer, ~line 754) and styles.ts .table-wrap: use a compact style (smaller type, tight cell padding) for tables with many short columns, so they fit the 756 px column.

## F963 (medium): GitHub file view: the folder path links and the branch picker / Go to file are gone

Found by: T3-tools. Where: https://github.com/preactjs/preact/blob/main/hooks/src/index.js at 1280 px

Evidence: Sift shows the header, Repository navigation, H1 'index.js', a collapsed 'Details' (Copy path, History, Blame, Raw, Copy raw file, Download raw file) and the code. Sift has no link or button named preact, hooks, src, main or Go to file (the eval returned []). The original shows the breadcrumbs 'preact / hooks / src / index.js' (links to /tree/main, /tree/main/hooks and /tree/main/hooks/src), the 'main' branch picker, 'Go to file' and the file tree. In Sift a reader cannot go up to the folder or switch branch. The only way back is the 'Code' tab, to the repo root. At 640 px Sift does show 'Files' and 'main branch' buttons. Round 8's shot of the same view (R8-T3-gh-blob.png) looks the same, so this is not new. Shots: /home/nico/projects/sift-test-3/research/shots/R9-T3-gh-blob-1280.png, /home/nico/projects/sift-test-3/research/shots/R9-T3-gh-blob-orig.png

Repro: cd /home/nico/projects/sift-test-3; export SIFT_PORT=9463 SIFT_TAB=T3-tools; bun scripts/act.ts "goto:https://github.com/preactjs/preact/blob/main/hooks/src/index.js" wait:9000 outline "eval:(()=>{const r=document.querySelector('sift-root').shadowRoot;const s=[...r.querySelectorAll('a,button')].map(e=>(e.innerText||e.getAttribute('aria-label')||'').trim()).filter(t=>/^(preact|hooks|src|main branch|Go to file|Files|main)$/i.test(t));const o=[...document.querySelectorAll('a,button')].filter(e=>e.getBoundingClientRect().height>0).map(e=>(e.innerText||e.getAttribute('aria-label')||'').trim()).filter(t=>/^(preact|hooks|src|main)$/i.test(t));return 'sift: '+JSON.stringify(s)+' orig visible: '+JSON.stringify(o)})()"  (prints sift: [] orig visible: [preact, main, preact, hooks, src])

Suspected cause: The breadcrumb bar and the file-tree pane (which holds the branch picker and Go to file) are dropped as navigation chrome on wide screens.

Skeptic: Partly refuted, partly confirmed. The claim that the folder path links are gone and a reader 'cannot go up to the folder' is false. Sift's Menu sheet on this blob page has preactjs→/preactjs, preact→/preactjs/preact, and the breadcrumb links preact→/tree/main, hooks→/tree/main/hooks and src→/tree/main/hooks/src. T3's eval only searched the closed view. What is confirmed, on 2 loads at 1280 px: the branch picker, 'Go to file' and the file tree pane are missing from Sift, both on the blob view and on the folder view /tree/main/hooks/src. Original with Sift off shows the 'main' picker, 'Go to file' and the tree. At 640 px, Sift shows 'Files' and 'main branch' (I reproduced this). The repo root in Sift at 1280 also has 'main branch' and 'Go to file'. So on any page below the root, a desktop-width reader cannot switch branch or jump to a file without going back to the root. This is a real loss of working controls, inconsistent across widths. It is medium-low, not the medium the claim gives it on the path-link grounds.

Skeptic's fix lead: src/content/extract/generic.ts: the rule that drops GitHub's wide-screen left pane (the file-tree column holding the ref picker and 'Go to file') as side navigation. Keep a side column that holds a form control or branch/ref picker (it is already kept at 640 px), or at least its header controls. Optionally also surface the breadcrumb near the H1, instead of only inside the Menu sheet.

## F964 (medium): OpenStreetMap directions: the route map sits below the whole step list, about two screens down

Found by: T3-tools. Where: https://www.openstreetmap.org/directions?engine=fossgis_osrm_foot&route=37.7961731%2C-122.3936846%3B37.8023791%2C-122.4058344

Evidence: After a route is computed (Foot, 'Distance: 1.7km. Time: 0:22.'), Sift's order is: mode radios, service select, From, To, Close, Reverse Directions, Close, the 19-row step table, then the map. The map portal's top is at 1720 px (448 px tall) in a 2295 px page, with an 813 px viewport. To see the route the user scrolls past every step, and back up to change the mode or fields. The original at 1280 px shows the directions sidebar beside the map, so both are on screen. Round 8's shot R8-T3-osm-route-foot.png has the same order, so this is not new. Google Maps in Sift puts the map first. Shot: /home/nico/projects/sift-test-3/research/shots/R9-T3-osm-dir-foot.png

Repro: cd /home/nico/projects/sift-test-3; export SIFT_PORT=9463 SIFT_TAB=T3-tools; bun scripts/act.ts "goto:https://www.openstreetmap.org/directions?engine=fossgis_osrm_foot&route=37.7961731%2C-122.3936846%3B37.8023791%2C-122.4058344" wait:8000 "eval:(()=>{const r=document.querySelector('sift-root').shadowRoot;const p=r.querySelector('.portal').getBoundingClientRect();return 'portal top='+Math.round(p.top+r.host.scrollTop)+' steps='+r.querySelectorAll('main table tr').length+' vh='+innerHeight})()"  (prints portal top=1720 steps=19 vh=813)

Suspected cause: The F874 change places a panel drawn to the right of the map after the map. The directions sidebar is drawn to the map's left, so it keeps coming first, with the long step table.

Skeptic: Reproduced on 2 loads of the OSM foot route ('Distance: 1.7km. Time: 0:22.'). The map portal's top was at 1685 px (448 tall), below the step table (725 to 1557 px, 20 rows). The viewport is 813 px. After clicking Car (2.5km 0:06), the map's top was at 1186 px in the viewport, still off screen. So a mode change shows no visible route change without scrolling past all steps, and then back up. Original: the sidebar sits beside the map, so both are visible. This is the same class of problem as F874 (the Layers panel pushing the map below the first screen), which the round 8 skeptic accepted as medium-low. It is a usability problem on a tool page, not pixel polish.

Skeptic's fix lead: src/content/extract/generic.ts, the panel/portal ordering that the F874 change touched: when a side panel beside a map portal holds a form plus a long results table (OSM's directions sidebar), place the portal after the form controls and before the step table, as Sift does for Google Maps routes. Or keep the panel's fields first and the map before any list over a few rows.
