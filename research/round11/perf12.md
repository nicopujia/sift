## F1111 (high, regression): Extraction became quadratic on long runs of same-length siblings: core-budget freezes the page for minutes (new marqueeCopies)

Found by: T6-fixtures. Where: http://127.0.0.1:8799/fx/core-budget.html (6000 comment divs, each with Reply/Like); src/content/extract/generic.ts marqueeCopies (lines 3885-3903), called from the child walk at ~3861

Evidence: I ran extraction-only bundles on the same page, one after the other, in the same headless Chrome. Round 10 code (scratchpad r10t6/r10.js): 3693/2751 ms. Merged src (r11t6/r11.js): 126567/112078 ms. The outline is identical. Scaling the comments: 1000 comments 1187 -> 5952 ms, 2000 comments 2939 -> 10258 ms. No other fixture out of 164 got slower than 2x. In the extension, Sift on: page.goto took 218 s to reach domcontentloaded, and the original and Sift both first answered at 387 s (one unresponsive gap of 169 s). scripts/firstpaint.ts gives -1/-1 because the page does not answer within its 15 s. The same page with Sift switched off: first content at 2.4 s. A Chrome running the round 10 base build (sift-r10-base built into scratchpad, port 9486): 23.0 s and 21.4 s. CPU profile of one extract(): 85.5 s self time in key() inside marqueeCopies, plus 15.1 s in querySelectorAll called from key(), plus 7.1 s in the \s+ regex.

Repro: SIFT_PORT=9466 ./scripts/chrome.sh start; SIFT_PORT=9466 SIFT_TAB=T6-fixtures bun scripts/firstpaint.ts http://127.0.0.1:8799/fx/core-budget.html "article p" 1 -> 'original -1 ms, sift -1 ms' (the page is frozen). Without the extension: cd /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r11t6 && bun prof.ts http://127.0.0.1:8799/fx/core-budget.html r11.js (about 2 minutes, prints the profile) and bun scale.ts 1000 2000 (round 10 bundle against the merged one)

Suspected cause: marqueeCopies (added for F1001) groups siblings by text length. For each sibling whose length equals an earlier one's, it calls key() on every earlier same-length sibling: textContent + regex + querySelectorAll('a[href]'), with no caching. 6000 comments that differ only in their number mostly share one length, so the cost is O(n^2) key builds. Fix lead: compute each element's key once (a Map, or a Set of keys per length) and only then compare; or skip the check past a small sibling count, since a marquee repeats a short strip.

Skeptic: Confirmed, high severity, and a regression. I built two extract-only bundles of my own: one from HEAD 0b07e6b and one from 7315d9a, the round 10 base, which has no marqueeCopies. I timed extract() in a plain headless Chrome with no extension. On fx/core-budget.html the base took 2401 and 2131 ms. HEAD took 88527 and 85590 ms. Both produced the same model, 1139796 bytes. Generated pages with N comments, base vs HEAD: 500 comments 327 vs 847 ms, 1000 comments 618 vs 3165 ms, 2000 comments 1103 vs 6613 ms. Growth follows the number of same-length siblings: comments 1000-5999 all have the same text length. I patched a scratch copy so each sibling's key() is computed once. That brought the fixture back to 3460 and 2731 ms, so marqueeCopies is the cause. In the extension on port 9466 with Sift on, firstpaint.ts printed -1/-1. My longer-timeout poll got domcontentloaded at 113.8 s. One evaluate call was blocked for 113 s. The original and Sift both first answered at 226.9 s.

Skeptic's fix lead: src/content/extract/generic.ts marqueeCopies (~3885): build key() once per element and keep a Set<string> of keys per text length. Then each sibling is one key build plus one Set lookup instead of a scan of every earlier same-length sibling with key() rebuilt on both sides. Optionally skip the check when ks is long (more than ~50 siblings), since a marquee repeats a short strip.

## F1112 (medium): r10-review: after choosing in the 'How long have you used it?' options sheet, focus falls to the top of main instead of returning to the combobox

Found by: T6-fixtures. Where: http://127.0.0.1:8799/fx/r10-review.html, the select-only combobox 'How long have you used it?' (keyboard and mouse)

Evidence: I focused 'How long have you used it? Choose one' and pressed Enter (focus goes to Close), then Tab ('Less than a week'), then Enter. The choice reaches the page ('Less than a week'), but focus lands on main#sift-main ('Write a review'), so a keyboard or screen reader user is sent back above the star rating. The button element was replaced (the old node is gone: same=false, isConnected=false). A mouse pick ('A few months') gives the same result. The original keeps focus on its combobox: the listbox mousedown is prevented, and pick() does not move focus. On r6-filterpop's 'Sort by' sheet, Sift returns focus to the opener ('Sort by Price: low to high'), so only this control is affected. The round 10 base build behaves the same, so this is not new.

Repro: SIFT_PORT=9466 SIFT_TAB=T6-fixtures bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r10t6/go.ts goto:http://127.0.0.1:8799/fx/r10-review.html wait:3000 "sx:([...R.querySelectorAll('button')].find(b=>/How long/.test(b.innerText)).focus(),1)" press:Enter wait:1000 press:Tab press:Enter wait:1500 focus -> 'focus: <main id="sift-main" tabindex="-1">'

Suspected cause: After the page changes, the combobox field (now rendered in place in FormView since F1012, src/content/ui/app.tsx) gets a new element key. The focused node is unmounted, and the sheet's focus return finds no opener, so it falls back to main. Keep a stable key for the field, or return focus by ref after the re-render.

Skeptic: Confirmed, medium severity, not a regression (I did not test the base build myself). On fx/r10-review.html I focused 'How long have you used it? Choose one' and pressed Enter, which moved focus to Close. Tab moved it to 'Less than a week' and Enter picked it. The page got 'Less than a week' (__log: used open, used Less than a week). Focus then ended on <main#sift-main>. I tagged the original button before opening. Afterwards it was disconnected, and the new button has the same data-ref='rf' with the label 'How long have you used it? Less than a week'. Same result on a second keyboard run and on two mouse runs that clicked 'A few months' inside the [role=dialog] sheet. Closing without a pick returned focus to the field, whose label had not changed. With Sift off (Alt+Shift+S), the same keys keep document.activeElement on #used after the pick. So Sift differs from the original. Likely cause: the focus restore for a sheet in src/content/index.ts (~381-385) finds a replaced opener only by tag and label, and the label changes to show the picked value. backToOpener (~3169) matches by data-ref, but in this case focus lands on main through the other path.

Skeptic's fix lead: src/content/index.ts, the spot.inSheet && opener branch (~381): when opener.el is disconnected, first look for the control with the same data-ref outside .layer/.suggest, as backToOpener does at ~3172. Fall back to the label match only after that. Optionally store the ref in the opener record (line ~890).

## F1110 (medium): React Aria date field in Sift: month and day are both named 'Reservation date', year is named 'yyyy', and all three boxes show 'Empty'

Found by: T5-amazon-gmail-a11y. Where: http://127.0.0.1:8799/fx/r10skep-ariadate.html (the real react-aria-components DateField that F1041's skeptic built). I found this during the F1041 recheck, not on my area's target pages.

Evidence: The CDP AX tree of Sift's view has spinbutton 'Reservation date' value=0, spinbutton 'Reservation date' value=0, spinbutton 'yyyy' value=0, then button 'Book'. Sift shows them as three stacked boxes, each with the visible text 'Empty', under the labels 'Reservation date', 'Reservation date' and 'yyyy'. A sighted user cannot tell which box is the month and which is the day, and a screen reader says 'Reservation date' twice. On the original, the segments have aria-label 'month, ', 'day, ' and 'year, ', each labelled by itself plus the field label, so they read as 'month, Reservation date' and so on, and they show inline as mm/dd/yyyy. Screenshot: /home/nico/projects/sift-test-5/research/shots/r11t5-ariadate.png. The round 10 skeptic already noted the 'Empty' labels, so this is not new.

Repro: SIFT_PORT=9465 SIFT_TAB=T5-amazon-gmail-a11y bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r11t5/axnames.ts http://127.0.0.1:8799/fx/r10skep-ariadate.html 6000 prints the three spinbuttons with those names. Then: bun /home/nico/projects/sift-test-5/scripts/act.ts shot:ariadate.

Suspected cause: Unverified lead: when Sift builds a field's label from aria-labelledby, it seems to drop the segment's own aria-label ('month, ', 'day, ') that a self-reference in aria-labelledby brings in. It also shows aria-valuetext ('Empty') as the visible value instead of the placeholder text (mm, dd, yyyy).

Skeptic: Confirmed, medium severity. I reproduced it twice on http://127.0.0.1:8799/fx/r10skep-ariadate.html, after a 6 s wait and again after 15 s. Sift's AX tree has spinbutton 'Reservation date', spinbutton 'Reservation date' and spinbutton 'yyyy', each with value 0. Each box shows the visible text 'Empty'. My screenshot is /home/nico/projects/sift-test-5/research/shots/skep-ariadate-sift.png. With Sift off, the original's AX tree reads 'month, Reservation date', 'day, Reservation date' and 'year, Reservation date', drawn inline as 'mm / dd / yyyy' (/home/nico/projects/sift-test-5/research/shots/skep-ariadate-orig.png). So month and day cannot be told apart in Sift, by sight or by screen reader. Neither the rejected lists nor F1041 cover the duplicate names; the round 10 skeptic only mentioned 'Empty' in passing.

The cause is not what the reporter suspected. A MutationObserver on page load showed that React Aria first inserts each segment with aria-labelledby pointing at an id that does not exist (':r6: :r1:'). About 40 ms later it rewrites the attribute to the segment's own id (':r5: :r1:'). Sift extracted in between, and it never re-reads after that change, because 'aria-labelledby' is not in the observer's attributeFilter (src/content/index.ts:2666). When I forced a re-extraction by appending a few words to a paragraph, the names became 'mm Reservation date', 'dd Reservation date' and 'yyyy Reservation date'. A static copy of the same DOM served from my scratchpad gives the same three names at once. So there is a second, smaller bug. idrefText in src/content/dom.ts reads a referenced node's innerText ('mm'), not its aria-label ('month, '), which the accessible-name algorithm uses for a self-reference. The visible 'Empty' comes from app.tsx's spinbutton case, which renders f.valueText (aria-valuetext) in place of the page's shown text.

Skeptic's fix lead: (1) In src/content/index.ts at line 2666, add 'aria-labelledby', 'aria-label' and 'id' to the MutationObserver attributeFilter. Then names a page fixes after mount get re-read. (2) In idrefText in src/content/dom.ts, use a referenced node's own aria-label when it has one, which covers the element referencing itself, and fall back to innerText otherwise. That gives 'month, Reservation date'. (3) In the spinbutton case of src/content/ui/app.tsx (around line 345), show the page's own text (for example a new 'shown' field set from textIn(el) in toField in generic.ts: 'mm', or '7') as the visible content. Keep aria-valuetext for screen readers only.
