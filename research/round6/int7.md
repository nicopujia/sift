## F628 (high, regression): Arrow keys and Space in a focused game board (or any focusable part of a shown original whose page handles keys on window) scroll Sift's view off the board

Found by: R2-interaction. Where: src/content/index.ts:941-962 (new round 5 keydown listener on window, bubble phase)

Evidence: New fixture fx/r6int-game.html: a canvas with tabindex=0 and a window keydown listener that calls preventDefault for the arrow keys and Space, as most canvas games do. At 1000x600 in Sift, I click the board (focus is on the canvas, the portal is entered) and press ArrowDown, ArrowDown, ArrowRight, ArrowUp, Space. The game gets all five keys, but Sift's view scrolls from 0 to 538 px (48+48-48+0.85 x view height, exactly scrollByKey's steps). The board is now at top -320, bottom 58, mostly off screen. The same keys on the original (Alt+Shift+S, same clicks) leave the page scroll at 0. Google Maps is not affected (its map div prevents the key itself: the map panned and Sift did not scroll).

Repro: SIFT_PORT=9467 SIFT_TAB=R2-interaction bun r6int/game.ts from the scratchpad dir (/tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad), with r6int/game-orig.ts as the control. By hand: open http://127.0.0.1:8799/fx/r6int-game.html, click the green board in Sift, press ArrowDown.

Suspected cause: The listener is added at document_start, so it runs before every window keydown listener the page adds later. It checks e.defaultPrevented before the game has had its turn, then calls preventDefault and scrollByKey itself. It also ignores enteredPortal(), so keys still scroll Sift after the user deliberately entered the original. Unity WebGL's template canvas (tabindex=-1, keys handled on window) fits this pattern. Fix ideas: skip when enteredPortal() === this portal's ref; or decide after the page's listeners have run (let the default scroll happen and mirror it, or register the listener lazily after load).

Skeptic: Reproduced twice on fx/r6int-game.html at 1000x600. In Sift I clicked the canvas, which focused it inside the portal. I pressed ArrowDown, ArrowDown, ArrowRight, ArrowUp, Space. The game logged all five keys, but Sift's scrollTop went from 0 to 538 and the board ended up at top -320, bottom 58. The control on the original (Sift off, same clicks and keys) left page scroll at 0, and that page can scroll: scrollHeight is 725 against a 600 px window, and PageDown on the body scrolls it to 125. So the game's preventDefault holds on the original and Sift overrides it. The code matches the claim. The listener at src/content/index.ts:944-962 is added on window at document_start, so it runs before any window keydown listener the page adds later. When it runs, e.defaultPrevented is still false, so it calls preventDefault and scrollByKey. It does not check enteredPortal(). The listener is not in the pre-round-5 source (scratchpad/pre-r5), so this is a regression. It only hits focusable boards whose page listens on window. Listeners on document or on the element run first and are not affected, which is why YouTube and Maps work. For those boards, the game cannot be played in Sift.

Skeptic's fix lead: src/content/index.ts:944-962. Decide after the page's own window listeners have run. For example, in a window capture-phase keydown listener, add a one-time bubble listener on window for that event. It runs last, so it sees the page's preventDefault, and only then does it mirror the scroll. Also return early when enteredPortal() === refOfPortal(portal), because the user has deliberately entered the original.

## F629 (high): Pressing a button or Submit inside a page popup that changes nothing in the DOM removes the popup from Sift (the F529 failure through H.act and H.submit)

Found by: R2-interaction. Where: src/content/index.ts:2229-2233 (afterAct without keep), called from H.act at index.ts:2449 and H.submit at index.ts:2567; src/content/recent.ts:17-26; src/content/extract/generic.ts:5204 (lastPop only with a text field) and generic.ts:5374 (a newsletter-worded dialog is kept only while recentNodes(true) points into it)

Evidence: (1) Existing F48 fixture fx/ext2-newsletter-open.html: Subscribe opens the role=dialog sheet. I type 'nico' in its email field (the page gets 'nico') and press the sheet's Subscribe. Sift shows the notice 'Email: Please include an '@'...', but the sheet is gone at 300 ms, 1.5 s and 4 s. Focus jumps to the page's Subscribe button, and the page dialog is still open. The user cannot fix the address. The same happens on new fixture fx/r6int-dlgform.html with an empty required email. (2) New fixture fx/r6int-sharepop.html: a role-less 'Servings' popup with Double it, Halve it, Done. 'Double it' only runs JS, so the DOM does not change. After one press the sheet is gone, focus is on Servings, and the page popup stays open. Pressing Servings again shows nothing (the page's handler returns early), so Halve it and Done cannot be reached without switching to the original.

Repro: From the scratchpad dir: SIFT_PORT=9467 SIFT_TAB=R2-interaction bun r6int/news2.ts (newsletter, invalid email), bun r6int/dlgform2.ts (required email), bun r6int/sharepop2.ts (role-less popup, plus the retry).

Suspected cause: afterAct() calls armRecent() without keep, which empties the recent nodes and byAction. Only those nodes keep a role-less popup (findPopup; the lastPop fallback needs a text field) or a cookie/newsletter-worded dialog (the NOISE_TEXT check). The F529 fix passes keep only from H.check and H.select. H.act and H.submit should do the same when the element (or form) is inside the shown dialog (inShownDialog).

Skeptic: Reproduced twice each. (1) On fx/ext2-newsletter-open.html, Subscribe opens the sheet. I typed 'nico' (the page field got 'nico') and pressed the sheet's Subscribe. The notice 'Email: Please include an '@'...' shows. The sheet is gone at 300 ms, 1.5 s and 4 s, focus is on the page's Subscribe button (r3), and the page's role=dialog is still open. Sift's outline has no email field left. (2) On fx/r6int-dlgform.html, pressing Sign up with the required email empty gives the same result: no sheet from 100 ms to 4 s, and the page dialog stays open. Pressing Subscribe again in Sift brings nothing back, because the page's handler returns early while .dlg exists. On the original (Sift off), the same press keeps the dialog open and moves focus to the email field. (3) On fx/r6int-sharepop.html, Servings opens the sheet. After 'Double it' the sheet is gone, focus is on Servings, and the page popup is still there. Pressing Servings again shows nothing, so Halve it and Done cannot be reached. The code matches the claim. H.act (index.ts:2449) and H.submit (index.ts:2567) call afterAct() without keep, so armRecent() empties the recent nodes. Only the F529 path (H.check and H.select) passes keep when the element is inside the shown dialog (inShownDialog). This is the F529 failure through two more handlers. In Sift, the user cannot fix an invalid email or finish a role-less popup.

Skeptic's fix lead: src/content/index.ts. In H.act, compute keep = inShownDialog(el) before the click and call afterAct(keep). In H.submit, compute keep = inShownDialog(form ?? fieldEl) and call afterAct(keep), at least when proxy.submit reports a problem. Optionally, widen the lastPop fallback in src/content/extract/generic.ts (around 5204) to popups without a text field.

## F630 (medium, regression): At 200% zoom or phone width, a notice now covers the whole top bar (site name, search box, Search, Menu) while the view is at the top

Found by: R2-interaction. Where: src/content/ui/styles.ts:40 (.bar[data-flat] .bar-notice { position: fixed; top: 0 }); src/content/ui/app.tsx:1037 and 993

Evidence: New fixture fx/r6int-topform.html: a header with nav and a search form, then a short contact form with a required email. At 640x450 (200% zoom) the bar is flat. Before Send, 'Search the bakery', Search and Menu are all visible at the top. After Send with the email empty, and with the view at the top, elementFromPoint at the center of each of those controls hits the notice ('COVERED by notice'). The screenshot (r6int/topnotice.png) shows only the yellow notice where the bar was. A validation notice stays until the user types or acts. A toast with Undo stays as long as the page shows it. Before round 5 the notice sat inside the static bar, below its controls.

Repro: From the scratchpad dir: SIFT_PORT=9467 SIFT_TAB=R2-interaction bun r6int/topnotice.ts 640x450

Suspected cause: The F530 fix fixes the notice at top:0 whenever the bar is flat, also when the flat bar itself is in view. Fix ideas: use position: sticky (it then sits below the bar while the bar shows and sticks at the top once the bar scrolls away), or fix the notice only while the bar is out of view.

Skeptic: Reproduced on fx/r6int-topform.html. At 640x450 the bar is flat and the page is only 455 px tall, so after Send the view is at the top without any forced scroll (scrollTop 5). The notice 'Your email: Please fill out this field.' then covers the site name, 'Search the bakery', Search and Menu. elementFromPoint at each control's center hits the notice, and my screenshot shows only the notice where the bar was. The notice was still there after 8.8 s. Shift+Tab from the email field puts keyboard focus on Menu, Search and the search box in turn, and each one is fully hidden under the notice (WCAG 2.4.11, Focus Not Obscured). At 390x844 the search box, Search and the site name are covered and Menu is visible. The cause is the F530 fix in src/content/ui/styles.ts:40: .bar[data-flat] .bar-notice is position: fixed at top: 0 even while the flat bar is in view. Before round 5 the notice sat below the controls, so this is a regression. It hits the low-vision 200% zoom users the F530 fix was meant to help. It lasts as long as a notice shows, so medium severity.

Skeptic's fix lead: src/content/ui/styles.ts:40 and src/content/ui/app.tsx (fitBar and the notice markup). Fix the notice only while the bar's control row is out of view, for example with an IntersectionObserver or a scroll check in fitBar that toggles an attribute on the bar. Or render the notice as a sibling after the header with position: sticky; top: 0 against the scroller. Sticky inside the static header would not work, because it scrolls away with the header. Keep --bar-h in sync.
