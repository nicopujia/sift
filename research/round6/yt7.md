## F620 (medium): Opening a video by single-page navigation shows a generic view titled 'YouTube' above the player for 2-8 s, then jumps to the real layout

Found by: T1-youtube. Where: YouTube: clicking a video or Mix in Sift on search results or home (single-page navigation to /watch)

Evidence: Polled every 100 ms after the click (t1r6/spapoll.ts), 3 of 3 navigations. Search -> Mix: 'h1=YouTube@96 portal=144 seek=false first=h1.,figure.portal-wrap' from 3.9 s to 12.1 s. Search -> video (pp= link): from 1.9 s to 4.2 s. Home -> Mix: from 1.7 s to 6.3 s. Then the layout switches to the player at 95 with the real H1 below it at 633 (a jump of about 540 px for the title). In this interim view the seek slider and the metadata are missing. The adapter view lands exactly when the original's #title h1 fills, so only the interim view is wrong. The original shows an empty title area in that window, not 'YouTube'. On fresh loads this no longer happens (F309). Shots: /home/nico/projects/sift-test-1/research/shots/R6T1-spa-youtube-h1-1.png, R6T1-spa-youtube-h1-0.png, contact sheet R6T1-spa-contact.png.

Repro: cd /home/nico/projects/sift-test-1; SIFT_PORT=9461 SIFT_PORT=9461 SIFT_TAB=T1-youtube bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/t1r6/spapoll.ts 'https://www.youtube.com/results?search_query=rick+astley' 'main li a.title[href*="dQw4w9WgXcQ"]' 14000. It prints 'h1=YouTube@96 portal=144 ... first=h1.,figure.portal-wrap' for several seconds before 'h1=Rick Astley - ...@633 portal=95'. Also try 'https://www.youtube.com/' with the same selector.

Suspected cause: After a single-page navigation, watch() in src/content/adapters/youtube.ts returns null while the watch metadata is not ready, and the generic extractor renders document.title ('YouTube' during YouTube's navigation) as the H1. watchSettling() and the early-title path appear to cover only the first load.

Skeptic: Reproduced in 3 of 3 single-page navigations with T1's spapoll.ts. Search to Mix: h1=YouTube@96 from 155 ms to 3081 ms, with the portal at 144 once it appears. Search to the second video: the same from 240 ms to 3564 ms. Home to Mix: the same from 148 ms to 2856 ms. Each time the view then switched to the player at 95 and the real H1 at 633. During that window the original's ytd-watch-metadata #title h1 was empty. In one run document.title already named the video at 1389 ms, but the H1 still said 'YouTube'. The suspected cause is wrong. The generic extractor is not involved. The YouTube adapter makes this view itself. With no title yet, watch() in src/content/adapters/youtube.ts returns a partial page: in the !flexy branch it is base([loading], 'YouTube'), and in the flexy branch it is base([player], ... || 'YouTube'), with no title block in either. App() in src/content/ui/app.tsx then draws page.title as a separate h1 (showTitle) above the blocks. When the title arrives, the H1 moves below the player. This is a real layout jump of about 540 px on every video opened in place, plus a wrong heading.

Skeptic's fix lead: In src/content/adapters/youtube.ts watch(), for the partial page with no title (the !flexy branch when not on first load, and the !fresh branch), do not fall back to 'YouTube' as page.title. Pass an empty title, so App() draws no stand-alone h1, or put the title-keyed h block after the player (use docTitle once it no longer reads 'YouTube' or the previous page's title). Then the H1 stays below the player and does not jump.

## F621 (medium): Opening a video tells screen readers 'YouTube' and never the video's title

Found by: T1-youtube. Where: YouTube: single-page navigation from search or home to a watch page (Sift's role=status live region)

Evidence: I recorded the polite status region (t1r6/announce2.ts). Search -> 'Rick Astley's Never Gonna Give You Up' gave only one entry: "1159ms 'YouTube'". 14 s later document.title was 'Rick Astley - Never Gonna Give You Up (Official Video) (4K Remaster) - YouTube', and Sift's H1 had shown that title since 4.1 s. Home -> Mix: 'YouTube' at 973 ms, and the region still said 'YouTube' about 20 s later. Home -> another video: 'YouTube' at 412 ms. By contrast, a search announces 'Search: rick astley' and Back announces 'Home' correctly (t1r6/announce3.ts). A screen-reader user who opens a video never hears which video opened.

Repro: cd /home/nico/projects/sift-test-1; SIFT_PORT=9461 SIFT_TAB=T1-youtube bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/t1r6/announce2.ts 'https://www.youtube.com/results?search_query=rick+astley' 'main li a.title[href*="dQw4w9WgXcQ"][href*="pp="]' 14000. It prints the status text changes ('YouTube' only) and the final document.title (the video's title).

Suspected cause: src/content/index.ts around lines 1638-1652. On navigation, page.title is YouTube's placeholder 'YouTube'. From search it differs from prevTitle, so 'YouTube' is said at once and titleWait is false. From home, prevTitle is also 'YouTube', so the 2.5 s timer fires while the title is still the placeholder. The real title, which arrives 4-12 s later, is never said.

Skeptic: Reproduced twice with T1's announce2.ts. Home to Mix: the polite region said only 'YouTube' at 520 ms. Search to the 'Never Gonna Give You Up' video: only 'YouTube' at 630 ms. After 12-14 s, document.title was the full video title, and Sift's H1 had shown it since about 3 s, but nothing more was announced. The code matches. In src/content/index.ts (navigation branch around lines 1638-1652), the first navigated page is the adapter's partial watch page titled 'YouTube'. When that differs from prevTitle, it is said at once and titleWait is set to false. When it equals prevTitle (from home), the 2.5 s timer says 'YouTube'. Either way, the real title that comes later is never announced.

Skeptic's fix lead: In src/content/index.ts, where navigated pages are announced, treat a page.partial page as not yet named. Set titleWait when page.partial or page.title === prevTitle. Have the timer and the 'titleWait && page.title !== prevTitle' branch announce only once the page is no longer partial. Also stop using the 'YouTube' placeholder as the title of partial watch pages in src/content/adapters/youtube.ts watch().

## F622 (medium): A timestamp link in a comment seeks the video, but Sift stays down in the comments; the original scrolls up to the player

Found by: T1-youtube. Where: YouTube watch page, Comments, timestamp links (e.g. '0:22' in a comment under Newest)

Evidence: In Sift, clicking '0:22' (href watch?v=dQw4w9WgXcQ&t=22s) changed currentTime from 96.5 to 24.5 and left the URL unchanged. The view stayed in the comments with the player's portal at top -2322, so the reader cannot see the jump. In original mode (Alt+Shift+S), clicking the same link at scrollY 1792 seeked (t=25.3) and scrolled the page to scrollY 0, which puts the player in view. Shot of the original after the click: /home/nico/projects/sift-test-1/research/shots/R6T1-orig-timestamp.png. Transcript lines behave the same in Sift (they seek, and the player may be far above). On the original, the transcript sits beside the player.

Repro: cd /home/nico/projects/sift-test-1; SIFT_PORT=9461 SIFT_TAB=T1-youtube bun scripts/act.ts goto:https://www.youtube.com/watch?v=dQw4w9WgXcQ wait:11000 click:Comments wait:3000 'click:Sort comments' wait:1000 click:Newest wait:4000 "eval:[...document.querySelector('sift-root').shadowRoot.querySelectorAll('details a')].filter(a=>/^\d+:\d\d$/.test(a.innerText)).map(a=>a.innerText)". Then click one of those, e.g. click:0:22 wait:2000, and run "eval:document.querySelector('video').currentTime+' '+document.querySelector('sift-root').shadowRoot.querySelector('.portal').getBoundingClientRect().top". The time changes, and the portal top stays far negative. Do the same with Alt+Shift+S on the original link: scrollY goes to 0. Timestamp comments vary; any comment with a time link works.

Suspected cause: The click is replayed on the original link. YouTube's handler seeks and scrolls the hidden original window to the top. Sift does not mirror that scroll-to-player in its own view.

Skeptic: Reproduced twice. Comments sorted by Newest held a comment with the timestamp links 0:22 and 0:54 (href watch?v=dQw4w9WgXcQ&t=22s / 54s). In Sift, clicking 0:54 seeked (24.9 to 56.4 s) and the URL stayed the same. The window scrollY went to 0, but Sift's view stayed in the comments with the portal top at -3268 (screenshot research/shots/skeptic-n2-sift.png). Clicking 0:22 later did the same: currentTime 24.4, portal top -3298. In the original (Alt+Shift+S), clicking the same 0:22 link at scrollY 2218 seeked to 24.5 and scrolled to scrollY 0, which shows the player (research/shots/skeptic-n2-orig.png). So the seek is replayed, but Sift drops the second half of the effect, which is bringing the player into view.

Skeptic's fix lead: In src/content/adapters/youtube.ts, mark comment and description links that point to the current video with a t= value as seek links. Then, in the click-replay path in src/content/index.ts (afterAct or the link-click handler), scroll the player's portal placeholder into view after such a click. A more general option: after a replayed click, if the original window scrolled so that a portal's element came into view, scroll Sift's view to that portal.

## F623 (medium): Settings dialog keeps the last sub-page's name ('Appearance', 'Display language') after Back or when reopened

Found by: T1-youtube. Where: YouTube (any page), header Settings dialog and its sub-pages

Evidence: Settings, then Appearance, then Back: the dialog lists the top-level items ('Your data in YouTube | Appearance: Light | Display language | ... | Keyboard shortcuts | Settings | Help | Send feedback'), but its visible heading and aria-label stay 'Appearance' (3 of 3 runs). The original's ytd-multi-page-menu-renderer shows the top-level list at that moment. Escape from Display language, then reopening Settings: the dialog is named 'Display language' while it lists the top-level items (2 of 2). Screen-reader users hear the wrong dialog name. In 1 of 3 runs in this stale state, clicking 'Keyboard shortcuts' did nothing: no dialog opened, and focus stayed on the button. That did not reproduce in 2 retries. Shot: /home/nico/projects/sift-test-1/research/shots/R6T1-settings-back.png

Repro: cd /home/nico/projects/sift-test-1; SIFT_PORT=9461 SIFT_TAB=T1-youtube bun scripts/act.ts goto:https://www.youtube.com/watch?v=dQw4w9WgXcQ wait:12000 click:Settings wait:1500 click:Appearance wait:1500 click:Back wait:1500 "eval:(()=>{const d=[...document.querySelector('sift-root').shadowRoot.querySelectorAll('[role=dialog]')].find(d=>d.checkVisibility());return d.getAttribute('aria-label')+' | '+d.innerText.replace(/\s+/g,' ').slice(0,120)})()". It prints 'Appearance | Appearance Close Your data in YouTube Appearance: Light Display language...'. Also try press:Escape, click:Settings, click:'Display language', press:Escape, click:Settings, then the same eval: 'Display language | ...'.

Suspected cause: The dialog's title is kept from the sub-page model when YouTube swaps the multi-page menu back to its top-level page (its header element stays in the DOM but hidden), so the title is read from a stale or hidden header.

Skeptic: Reproduced. Settings showed 'label=Settings'. Then Appearance showed 'label=Appearance', with Back and the theme choices. After Back, the dialog showed 'label=Appearance h2=Appearance' while listing the top-level items. The original at that moment: the top-level menu's visible #header is empty, and the only header with the text 'Appearance' is in the hidden submenu (checkVisibility false). Escape, then Settings again: the dialog was still named 'Appearance'. After Display language and Escape, reopening Settings gave 'label=Display language', with focus on Close. So the wrong name stays for the rest of the visit, and a screen reader announces it on open. The side claim did not reproduce: from the stale state, Keyboard shortcuts opened normally. The cause is in settingsMenu() in src/content/adapters/youtube.ts. `q("ytd-simple-menu-header-renderer", page)` searches the whole subtree of the top-level menu, so it finds the hidden submenu's header, and its h2 becomes the title.

Skeptic's fix lead: In src/content/adapters/youtube.ts settingsMenu(), pick the header that belongs to the page being shown and is visible: qa("ytd-simple-menu-header-renderer", page).find(h => h.closest("ytd-multi-page-menu-renderer") === page && visible(h)). For the top-level page, the title then falls back to the opener's aria-label ('Settings').

## F624 (medium): Picking an item in a playlist or Mix closes the playlist section, while the original keeps its panel open

Found by: T1-youtube. Where: YouTube watch page with &list= (a playlist such as PL2MI040U_GXobmpXtTwBF7oHBGT5BETSD, or the Mix RDdQw4w9WgXcQ): the playlist/Mix section

Evidence: I opened the 'Mix - Rick Astley ...' section and clicked its first item (it plays). After navigation the section had open=false, H1 and portal were correct, and focus was on main at the top. The original's ytd-playlist-panel-renderer stayed visible and expanded. Same on the 'RickAstley - Greatest Hits · 1 / 10' playlist: after clicking item 3 and then item 2, the summary updated to '3 / 10' and '2 / 10', but open=false both times. Those two targets showed YouTube's bot check. Working through a playlist by keyboard means reopening the section and finding the current item after every video. Sift's media bar has no Next or Previous video either, and YouTube's in-player Next is not on the Tab path. Shot: /home/nico/projects/sift-test-1/research/shots/R6T1-mix-next.png

Repro: cd /home/nico/projects/sift-test-1; SIFT_PORT=9461 SIFT_TAB=T1-youtube bun scripts/act.ts 'goto:https://www.youtube.com/watch?v=dQw4w9WgXcQ&list=RDdQw4w9WgXcQ&start_radio=1' wait:12000 'click:Mix - Rick' wait:800 'click:performs “Never Gonna Give You Up” in' wait:6000 "eval:[...document.querySelector('sift-root').shadowRoot.querySelectorAll('details')].find(d=>/^Mix/.test(d.querySelector('summary').innerText)).open+' '+document.querySelector('ytd-playlist-panel-renderer#playlist').checkVisibility()". It prints 'false true'. The item texts are AI one-liners and can vary; any item in the open Mix shows the same result.

Suspected cause: After a single-page navigation the section's open state is reset to its default (collapsed), possibly because the remembered key depends on the video, even when the list is the same.

Skeptic: Reproduced 3 times. On watch?v=dQw4w9WgXcQ&list=RDdQw4w9WgXcQ I opened the Mix section (open=true) and clicked an item. The first item (same video, &index=, no bot check) gave siftOpen=false while the original's ytd-playlist-panel-renderer stayed visible with no collapsed attribute. The second and third items gave the same result. Those two also showed YouTube's bot check, which does not change this logic. The suspected cause is wrong. The section key is a fixed 'playlist'. Instead, checkUrl() in src/content/index.ts (around line 1775) calls store.local.clear() on every single-page URL change, which also wipes 'sec:playlist'. Section() in src/content/ui/app.tsx then falls back to collapsed: true. Every video picked from a list closes the list.

Skeptic's fix lead: In src/content/index.ts checkUrl(), keep the 'sec:playlist' entry in store.local, instead of clearing it, when the old and new URLs have the same list= parameter (or keep any sec:* entry the adapter marks as persistent across navigation). Optionally key the section by list id in playlistSection() in src/content/adapters/youtube.ts, so a different list starts collapsed.
