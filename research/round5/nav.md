After one PageDown, each Home press steps the original up one screen, so it takes about 12 presses. Round 4 opened this thread on 'zugzwanged,Anlis,Schard'. Skeptic: Reproduced on 3 fresh loads. In the first, scrollY was 0 at 1.5 s with Sift showing 'zugzwanged,Anlis,Schard'. At 3.5 s scrollY was 10593 and Sift showed 'burumdev,khimru,jumpnbrownweasel'; the URL became .../143208/18. The second load ended at scrollY 10593 and the third at 10506. After one PageDown, each Home press stepped the original up one screen, and it took about 9 presses to get back to zugzwanged. Code: fillScreen() in src/content/index.ts calls loadMore() when host.scrollHeight <= 2 * clientHeight, and loadMore() sets se.scrollTop = se.scrollHeight. Unlike the scroll handler, fillScreen() does not check cloakedPosts().

Skeptic's fix lead: In src/content/index.ts, make fillScreen() return early when cloakedPosts() is true, as the scroll handler does. Better, never jump the original to scrollHeight on a page that unloads its posts, and let stepWith() handle it. Also let Home, or wheel-up at Sift's top, call stepWith(false, -1) when the original's scrollTop > 0.

## F504 (high): Discourse topic list never loads more than the first 30 topics in Sift

Found by: T4-generic. Where: https://users.rust-lang.org/latest

Evidence: After 3 End presses with 4 s waits, Sift's view is at its bottom (scrollTop 1715 of 2615) and still has 30 rows. The original stays at scrollY 0 with 30 tr.topic-list-item. 8 wheel steps of 1500 px gave the same result. Sift has no load-more or next-page control. With Sift off, scrolling the original to its end loads 60 topics. Switching back to Sift then shows 60, so the mirroring works, but the trigger never fires. Older topics cannot be reached from Sift. Shot: /home/nico/projects/sift-test-4/research/shots/r5t4-discourse-latest-end.png

Repro: SIFT_PORT=9464 SIFT_TAB=T4-generic bun scripts/act.ts goto:https://users.rust-lang.org/latest wait:8000 press:End wait:4000 press:End wait:4000 press:End wait:4000 "eval:[document.querySelector('sift-root').shadowRoot.querySelectorAll('tbody tr').length, document.querySelectorAll('tr.topic-list-item').length, scrollY]" gives [30,30,0].

Suspected cause: The near-bottom trigger in src/content/index.ts runs loadMore only when shownItems(store.page.blocks) is non-zero. A topic list rendered as a data table has 0 items, and the page has no cloaked posts, so neither loadMore nor stepWith runs.

Skeptic: Reproduced on 2 fresh loads. After End x3 with 4 s waits, the result was [30 Sift rows, 30 original rows, scrollY 0]. Sift's scrollTop was 1776 of 2589, its bottom. 8 wheel steps of 1500 px on the first load and 10 on a second load gave the same result, with 0 li.item. Sift has no more, next or older control. With Sift off, wheel-scrolling the original loaded 180 topics, and switching back showed 180 rows in Sift, so the mirroring works and only the trigger is missing. shownItems() in src/content/index.ts counts only 'items' blocks (and those inside articles or sections), not table rows. So both the near-bottom scroll trigger and fillScreen() return early.

Skeptic's fix lead: In src/content/index.ts, let the near-bottom trigger (and fillScreen) count the rows of a table block (or any long repeated block) in shownItems(). Or let it run loadMore() when the original document can still scroll and its scrollHeight has grown after past nudges.

Continue your trip, tap the notification on your phone to get directions', '[button] Collapse side panel'. The alternatives list shows 'via Bay St | via Mason St | via Bay St | via Mason St'. The original has 3 h1s (via Bay St | via Mason St | via The Embarcadero N) and shows the chosen one. Shot: /home/nico/projects/sift-test-3/research/shots/R5-T3-gdir-alt.png

Skeptic: Reproduced 2 of 2. The defect is a spurious modal sheet, not an inline copy. Skeptic's fix lead: generic.ts findPopup/popupLike: Google re-renders the side panel after the click, so the panel counts as 'fresh' and `return fresh || …` accepts it, although it is a full-height panel. A root whose re-rendered headings duplicate the page view should never be a popup. That covers a panel that holds the directions form or route headings Sift already shows. Also, in titleH1, when several h1s are sibling route headings, use the selected or expanded route's h1, or docTitle, not the first one.

## F515 (medium): GitHub folder pages reached by in-app navigation show the previous page's title as H1

Found by: T3-tools. Where: https://github.com/preactjs/preact → click 'hooks' → click 'src'

Evidence: 2 of 2. On /tree/main/hooks/src, Sift's H1 is 'preactjs/preact: ⚛️ Fast 3kB React alternative with the same modern API…', the repo page's title. It is still there 15 s later, while document.title is 'preact/hooks/src at main · preactjs/preact'. Starting from /tree/main/hooks, the H1 after clicking src stays 'preact/hooks at main' (the previous folder). A direct load gives H1 'preact/hooks/src at main'. The file list below (H2 src, index.d.ts, index.js, internal.d.ts) is correct.

Repro: cd /home/nico/projects/sift-test-3; SIFT_PORT=9463 SIFT_TAB=T3-tools bun scripts/act.ts goto:https://github.com/preactjs/preact wait:10000 click:hooks wait:5000 click:src wait:15000 "eval:document.querySelector('sift-root').shadowRoot.querySelector('h1').innerText+' | '+document.title"

Suspected cause: With no visible page h1, the H1 comes from document.title at extraction time. GitHub updates the title after Sift's re-extraction for the soft navigation, and no later run picks it up.

Skeptic: Reproduced 2 of 2. Repo home → click 'hooks' → click 'src': on /tree/main/hooks/src, Sift's H1 is 'preactjs/preact: ⚛️ Fast 3kB React alternative…' after 15 s. document.title is 'preact/hooks/src at main · preactjs/preact · GitHub'. Direct /tree/main/hooks → click 'src': H1 stays 'preact/hooks at main' after 15 s. A direct load of /hooks/src gives 'preact/hooks/src at main'. The page's visible h1 'src' is skipped: titleH1 requires textIn(h).length > 3, so the title falls back to docTitle. That runs before GitHub updates <title>, and nothing re-runs it. The 'hooks' page shows H1 'hooks' correctly because that h1 is long enough. A wrong page heading after navigation misleads screen reader users.

Skeptic's fix lead: generic.ts titleH1: accept short visible h1s (2 or more characters, e.g. 'src'). Also, in index.ts, re-extract (or refresh the title) when document.title changes after a single-page navigation, for example by observing the <title> element.

## F516 (high, regression): Opening an email or a video from a list announces 'Removed: <title>' instead of the new page's title

Found by: T5-amazon-gmail-a11y. Where: src/content/index.ts paint() (the new t('removed') check); seen on fx/gmail.html and live YouTube search

Evidence: Gmail fixture: focused the 'New gluten-free bakery list for San Francisco' link and pressed Enter. The URL became #inbox/2, and Sift's h1 is the subject. The only announcement in 4 s was 'Removed: New gluten-free bakery list for San Francisco.' (at 697 ms). The email was not removed: the fixture's mails array still holds id 2. A mouse click on 'Your class schedule for next week' gave 'Removed: Your class schedule for next week.' Live YouTube search 'sourdough bread': Enter on 'Step-by-step guide to baking sourdough bread' went to watch?v=4gEoh3sk2AE. The only announcement in 6 s was 'Removed: Step-by-step guide to baking sourdough bread.' Before the merge, run() said the new page's title. say() replaces any pending text after 100 ms, so the later 'Removed' cancels the title. history.back/forward still say the title ('Inbox', 'Your package was delivered'), because focus is not in a list item then.

Repro: cd /home/nico/projects/sift-test-5; SIFT_PORT=9465 SIFT_TAB=x bun scripts/act.ts goto:http://127.0.0.1:8799/fx/gmail.html wait:3000 "eval:(()=>{const r=document.querySelector('sift-root').shadowRoot;[...r.querySelectorAll('a')].find(a=>a.innerText.includes('bakery')).focus()})()" press:Enter wait:1500 "eval:[location.hash, document.querySelector('sift-root').shadowRoot.querySelector('[aria-live]').textContent]" "eval:mails.some(m=>m.id===2)"  (prints '#inbox/2', 'Removed: New gluten-free bakery list for San Francisco.', true). YouTube: load https://www.youtube.com/results?search_query=sourdough+bread, wait 9 s, focus the first watch?v= link in Sift's main, press Enter, read the [aria-live] text.

Suspected cause: paint() says t('removed') when the focused list item's title is gone and store.actAt is under 3 s old. It does not check that the page navigated (the URL changed, or navPending/navigated in run()). That say() also cancels the say(page.title) made just before.

Skeptic: Reproduced 3 times on the Gmail fixture and 2 times on live YouTube search. I put a MutationObserver on Sift's only live region ([aria-live=polite].sr). Gmail fixture: focus 'New gluten-free bakery list for San Francisco' and press Enter. The hash became #inbox/2 and Sift's h1 became the subject. In 4 s the only announcement was 'Removed: New gluten-free bakery list for San Francisco.' (at 205 ms the first time, 152 ms the second). mails.some(m=>m.id===2) was still true, so nothing was removed. A trusted mouse click on 'Your class schedule for next week' went to #inbox/1 and said only 'Removed: Your class schedule for next week.' YouTube search 'sourdough bread': Enter on the first video went to watch?v=4gEoh3sk2AE and said 'Removed: A step-by-step guide to baking sourdough bread.' at about 1.8 s. Then it said only 'YouTube' at 2.9 s, not the video's title. Enter on the second video went to watch?v=DiI-1PF_Mr0 and said only 'Removed: A beginner-friendly sourdough bread recipe.' The code matches the suspected cause. In run(), a navigation calls say(page.title) and then paint(). paint() calls say(t('removed')) whenever the focused item's title is no longer among the li.item titles and actAt is under 3 s old. It never checks whether the page navigated. say() clears the pending 100 ms timer, so the 'Removed' text replaces the page title. It is a regression: this check exists only in the round-4 int copy and in the merged tree. It misleads screen reader users on the most common action in list apps (opening an item), so high severity is fair.

Skeptic's fix lead: src/content/index.ts: make paint() skip the t('removed') announcement when the page navigated. One way is for run() to pass its 'navigated' flag into paint(), or to set a navAt timestamp that paint() checks. Another is to save location.href when store.actAt is set and announce 'Removed' only if location.href has not changed since. Either way, a navigation keeps say(page.title).

## F528 (high, regression): Opening a list entry in a single-page app announces 'Removed: <entry>' instead of the new page's title

Found by: R2-interaction. Where: src/content/index.ts:411-412 (paint's removed announcement), overriding say(page.title) at index.ts:1535 (say keeps only the last text within 100 ms, index.ts:425-433)

Evidence: Live YouTube home: I focused the first entry's title in Sift and pressed Enter. It opened the watch page, and the only thing the live region said was 'Removed: Rick Astley’s song “Never Gonna Give You Up”.' Fixture fx/gmail.html: Enter on the first email's title opens #inbox/1 (h1 'Your class schedule for next week'). The live region said only 'Removed: Your class schedule for next week.' New fixture fx/r5int-morenav.html (pushState to a recipe): 'Removed: Recipe number 2 with rice flour.' The page title is never said, and the user is told the entry they opened was removed.

Repro: From the scratchpad dir: SIFT_PORT=9467 SIFT_TAB=R2-interaction bun r5int/rm1.ts (Gmail fixture), bun r5int/more.ts (r5int-morenav), bun r5int/ytnav.ts (live YouTube home). Each records the .sr[aria-live] text after Enter or a click on an entry title.

Suspected cause: The F351 fix in paint() says 'removed' whenever the focused control was inside li.item, actAt is under 3 s old, and no li.item .title has the same text. A navigation from a list entry meets all three. run() calls say(page.title) before paint(), so the later say() replaces it. Fix: skip the removed announcement when this run navigated (pass `navigated` into paint, or compare the URL saved in spotOf with location.href).

Skeptic: Reproduced, and it is a regression: the 'removed' announcement is missing from sift-r4-base and present in sift-test-7. Gmail fixture, focus on the first entry's title and Enter, run twice: the URL goes to #inbox/1, the h1 is 'Your class schedule for next week', and the only live-region text is 'Removed: Your class schedule for next week.' A trusted mouse click on the second entry gives the same result: 'Removed: New gluten-free bakery list for San Francisco.' On r5int-morenav.html, clicking 'Recipe number 2 with rice flour' (pushState, run twice, no Load more needed) gives only 'Removed: Recipe number 2 with rice flour.' Live YouTube home: Enter on the first entry ('Rainy Velvet Jazz') opens /watch, and the only text said is 'Removed: Rainy Velvet Jazz.' In the code, paint() at index.ts:411-412 runs after run() has called say(page.title) at index.ts:1535. say() keeps only the last text within 100 ms, so the false 'Removed' replaces the page title. Every screen-reader user who opens a list entry in a single-page app is told the entry was removed and never hears the new page's title.

Skeptic's fix lead: In src/content/index.ts paint(), skip the removed announcement when the render came from a navigation. Options: have run() set a flag (such as navAt = Date.now() next to say(page.title)) that paint checks, or save location.href in spotOf() and require it to equal location.href before saying 'removed'.
