## F307 [medium] Sticky header takes over a quarter of the screen at 200% zoom
- **where**: YouTube watch and search at 200% zoom (viewport 640x450 CSS px, deviceScaleFactor 2)
- **evidence**: Sift's header (YouTube, Search field, Search, Menu, then Sign in and Settings on a second row) is position:sticky and 119 CSS px tall in a 450 px viewport (26%). It stays on screen while reading comments and covers part of every view, so low-vision users who zoom get the least room for content. No horizontal scroll (scrollWidth 640). Screenshots: /home/nico/projects/sift-test-1/research/shots/R4T1-watch-zoom200.png, R4T1-search-zoom200.png
- **repro**: Set the test tab to 640x450 at deviceScaleFactor 2 (puppeteer page.setViewport({width:640,height:450,deviceScaleFactor:2})). Load https://www.youtube.com/results?search_query=sourdough+bread and wait 12 s. Read getComputedStyle(shadowRoot.querySelector('header')).position ('sticky') and its height (119).
- **suspectedCause**: styles.ts keeps the header sticky at all widths and lets it wrap to two rows. At narrow or zoomed widths it could stop sticking or collapse Sign in and Settings into the Menu.
- **verdict**: Reproduced at 640x450 with deviceScaleFactor 2 on search and watch. Sift's header is position:sticky, 119 px tall, top 0. Search and Menu are at y 9-10, and Sign in and Settings wrap to a second row at y 64. It stays at top 0 and 119 px after scrolling. scrollWidth is 640, so there is no horizontal scroll. It takes 26% of the viewport.
- **fix**: In src/content/ui/styles.ts, under a max-height/zoom media query (for example @media (max-height: 500px) or (max-width: 700px)), make the header position:static. Or keep only a compact one-row search there and move Sign in and Settings into the Menu.

## F353 [medium] 'N new items' is announced repeatedly while pages load, with no user action, and says '1 new items'
- **where**: src/content/index.ts:1220-1221 (say(t('newItems')) whenever the item count grows on the same URL)
- **evidence**: I logged Sift's live regions every 100 ms after load, without scrolling. On live https://www.youtube.com/results?search_query=sourdough+bread: '4 new items' at 6.1 s, '6 new items' at 6.8 s, '1 new items' at 8.6 s, '3 new items' at 10.1 s and '6 new items' at 11.0 s. On the static amazon-search snapshot: '6 new items' at 1.9 s and '8 new items' at 2.7 s on another load. On the youtube-search snapshot: '26 new items' at 1.85 s. A screen reader user hears a stream of 'new items' while the first page is still being built.
- **repro**: Run bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/t5/livelog.ts "https://www.youtube.com/results?search_query=sourdough+bread" 12000 (SIFT_PORT/SIFT_TAB set). It prints each change of the text in Sift's [aria-live] regions.
- **suspectedCause**: Item growth during the initial load and hydration counts as 'new items'. It should be announced only after a user-triggered load more or scroll, and with a plural rule for 1.
- **verdict**: Reproduced, with no scrolling or input. youtube-search snapshot: '32 new items' at 1.6 s on run 1 and '23 new items' at 1.7 s on run 2. Live YouTube search for 'sourdough bread', run 1: '2 new items' at 3.8 s, '8 new items' at 4.8 s, '10 new items' at 5.8 s. Run 2: '1 new items' at 4.2 s, then 9, 9 and 7. The code matches: src/content/index.ts:1220-1221 announces whenever the item count grows on the same URL. It does not check for a user action. Sift's own fillScreen() loadMore nudges and initial hydration count too. t() in src/content/i18n.ts has no plural handling ('{n} new items').
- **fix**: In src/content/index.ts run(): announce newItems only when a user-triggered load happened recently, such as a timestamp set by the H.loadMore handler or a user scroll, not by fillScreen(). Skip it while store.booting or page.partial, or within the first few seconds after first paint. Add a singular string in src/content/i18n.ts ('1 new item' / '1 elemento nuevo') and pick it when n === 1.

## F354 [low] Filter and product links resolve against the page URL, not document.baseURI, so their hrefs differ from the original
- **where**: amazon-search snapshot (has <base href="https://www.amazon.com/">); Amazon adapter item and filter hrefs
- **evidence**: The original 'Sony' brand filter's .href is https://www.amazon.com/s?k=wireless+headphones&rh=p_123%3A237204…, but Sift's link href is http://127.0.0.1:8799/s?k=…. All 7 brand links and all 16 product title links show this (24 of 32 links). Pagination, Cart, Returns and 'Click to see price' do use amazon.com. A real click is replayed correctly (clicking 'Sennheiser' requested https://www.amazon.com/s?…p_123%3A213748…, blocked by my guard). Inferred, not tested: open in new tab, copy link and the hover URL point to the wrong address on any site whose <base href> differs from its URL.
- **repro**: Load http://127.0.0.1:8799/amazon-search, open Filters > Brands, and compare Sift's a.href for 'Sony' with the original's [...document.querySelectorAll('a')].find(a=>a.innerText.trim()==='Sony').href.
- **suspectedCause**: Some code paths build absolute URLs with new URL(href, location.href) instead of el.href or document.baseURI.
- **verdict**: Reproduced on the amazon-search snapshot, behind a CDP guard that blocked all amazon hosts. document.baseURI is https://www.amazon.com/ and location is http://127.0.0.1:8799/amazon-search. Sift had 27 links, and 17 of them resolved to http://127.0.0.1:8799/... One example is the Soundcore product link, http://127.0.0.1:8799/soundcore-Cancelling-Headphones-Bluetooth-Transparency/dp/B0C3HCD34R, while the original's a.href is https://www.amazon.com/soundcore-.../dp/B0C3HCD34.... Root cause, confirmed in code: absUrl() in src/content/dom.ts:647 does new URL(h, location.href), and generic.ts:4360 does the same. The browser resolves against document.baseURI. Scope: the base href here comes from serve.ts, so live amazon.com is not affected. Pages whose <base href> differs from their URL get wrong hrefs, which matters for open in new tab, copy link and the status bar. I did not test middle-click.
- **fix**: src/content/dom.ts absUrl(): use new URL(h, document.baseURI). Do the same at src/content/extract/generic.ts:4360. Or, where the element is at hand, use (el as HTMLAnchorElement).href.

## F357 [low] Pagination is not a navigation landmark
- **where**: Amazon search snapshot, the pagination row
- **evidence**: Sift renders the pager as <div class="row actions"> inside main. The original is <div role="navigation" aria-label="pagination">. Landmark lists in Sift show only header, form[role=search], main and form, so screen reader users cannot jump to the pager.
- **repro**: Find the row containing 'Previous' in Sift's shadow root and read its ancestors.
- **verdict**: Reproduced on the amazon-search snapshot. Sift's 'Previous' button sits in div.row.actions inside main, with no role. The landmarks in Sift's shadow root are header, form[role=search], main and form. The original's pager is <div role="navigation" aria-label="pagination">. The 'pages' actions block from amazon.ts results() carries no landmark information, so app.tsx cannot render one.
- **fix**: Add an optional nav label to the actions block in src/content/model.ts. Set it on the 'pages' block in src/content/adapters/amazon.ts results(), from the original's aria-label or 'Pagination'. In src/content/ui/app.tsx, render such actions blocks as <nav aria-label=...>. The generic extractor can set the same field when the source container has role=navigation.
