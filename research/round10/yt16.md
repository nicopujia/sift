## F1060 (medium, regression): Home: after a fast mouse-wheel flick, Sift stops at the end of its list and never loads more; wheel, End and PageDown then do nothing

Found by: T1-youtube. Where: https://www.youtube.com/ (Sift's main view, mouse wheel)

Evidence: Reproduced in 4 of 4 home runs. Each run did bursts of 25 wheel events of 2500 px, 50 ms apart, with 5 s between bursts. Results: 21 -> 45 -> 45 -> 45 (twice), 21 -> 69 -> 117 -> 117, and the round 9 home.ts run gave 45/45/45. In the stuck state, Sift's host is at its very end (scrollTop 3375 of scrollHeight 4275, clientHeight 900). The original stays at scrollY 3181-3203 of 7137, so it is never moved to its end. Slow wheel steps after that, then End and PageDown, all leave the list at 45. Only Home, then End, loads more (45 -> 93). Same pattern on the original with Sift off: 31 -> 175 -> 298 (its feed end). Same pattern on search and on watch comments: Sift keeps loading (search 40 -> 98 -> 170 -> 196; comments 20 -> 120 -> 160 -> 200 -> 260 -> 280). Slow wheeling on home works (21 -> 237 in 14 steps). works.md line 68 ('Wheel loads 141 / 237 / 381 against the original's 141 / 261 / 381') came from the same home.ts script in round 9. Shot: /home/nico/projects/sift-test-1/research/shots/r10t1-home-wheel-stuck.png (list end, folded Shorts, no more entries).

Repro: cd /home/nico/projects/sift-test-1; SIFT_PORT=9461 SIFT_TAB=T1-youtube K=25 DY=2500 GAP=5000 STEPS=3 bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/t1r10/wheelfast.ts (it prints 'sift li N' after each burst; it stalls at 45 or 69/117). Then SIFT_PORT=9461 SIFT_TAB=T1-youtube NOLOAD=1 STEPS=3 GAP=2500 bun .../t1r10/wheelhome.ts: slow wheel steps do not load more either. Original for comparison: bun .../t1r10/wheelorig.ts (it switches Sift off, wheels, and switches back).

Suspected cause: src/content/index.ts host scroll listener: load-more runs only on a scroll event that is 'near' the end and more than 1500 ms after lastNudge. During a fast flick, the first nudge loads 21 -> 45 and Sift's view runs to the new end within that 1500 ms. Once the view sits at its end, further wheel events fire no scroll event. edgeScroll() (the wheel handler at the edge) only acts for cloakedPosts() pages, so nothing calls loadMore again. A wheel or End at Sift's end of a loadable list could call askMore()/loadMore() as the scroll path does.

Skeptic: Reproduced on YouTube home. The reporter's flick (bursts of 25 wheel events of 2500 px) got stuck in 2 of 2 runs: at 21 -> 45 -> 45 -> 45, then 21 -> 69 -> 69 -> 69. In the stuck state Sift's host was at its very end (3346 of 4246 with clientHeight 900, then 5448 of 6348). The original was far from its end (doc 3228 of 7209), so it never loaded more. Three slow wheel steps, then End, then PageDown, all left the count unchanged. A moderate speed (10 x 300 px every 1.3 s) also got stuck at 69 in 1 of 2 runs; the other run loaded to the feed end (315). Runs on the original with Sift off went 31 -> 199 -> 292 (feed end). An earlier exact-repro run went 21 -> 93 -> 141 -> 165 without sticking, so it is timing-dependent, but it stuck in 3 of 4 runs that hit the timing. The code matches the cause. The host scroll handler in src/content/index.ts (around line 2655) drops a near-end scroll that comes within 1500 ms of lastNudge. Once the view sits at its end, wheel and keys fire no scroll event. edgeScroll (around line 2728) only acts when cloakedPosts() is true, so nothing calls loadMore again.

Skeptic's fix lead: In src/content/index.ts edgeScroll(), when dir > 0, the host is at its end, it is not cloakedPosts(), shownItems(store.page.blocks) is true and lastNudge is older than 1500 ms, set lastNudge and call askMore() and loadMore(), as the scroll handler does. Also, in the host scroll handler, when a near-end nudge is dropped only by the 1500 ms gate, set a timer that checks again once the gate expires and calls loadMore if the view is still near its end.

## F1061 (medium): Playlist page: Sift's header has no Settings, while YouTube's top bar shows Settings

Found by: T1-youtube. Where: https://www.youtube.com/playlist?list=PL2MI040U_GXobmpXtTwBF7oHBGT5BETSD (header)

Evidence: In 2 of 2 loads (15 s wait, and again after 20 more s), Sift's header had only 'Search | Menu | Sign in'. The original's masthead has 'Settings | Sign in', and ytd-masthead ytd-topbar-menu-button-renderer button[aria-label=Settings] is visible (checkVisibility true). Settings is in Sift's header on watch, home, search (English and Spanish) and Shorts. Sift's Menu has no Settings entry either (Home … Report history). So on this page, Appearance, Display language, Restricted Mode and Location cannot be reached. The page also looks like the generic extractor's output: raw titles, no one-liners, 'by Rick Astley' as a button, durations as '3 minutes, 34 seconds'. Shot: /home/nico/projects/sift-test-1/research/shots/r10t1-playlist-page.png

Repro: cd /home/nico/projects/sift-test-1; SIFT_PORT=9461 SIFT_TAB=T1-youtube bun scripts/act.ts "goto:https://www.youtube.com/playlist?list=PL2MI040U_GXobmpXtTwBF7oHBGT5BETSD" wait:15000 "eval:[...document.querySelector('sift-root').shadowRoot.querySelectorAll('header a, header button')].map(e=>(e.getAttribute('aria-label')||e.innerText).trim()).join(' | ')+' || orig: '+[...document.querySelectorAll('ytd-masthead #end button, ytd-masthead #end a')].filter(e=>e.checkVisibility()).map(e=>(e.getAttribute('aria-label')||e.innerText).trim()).join(' | ')" prints 'Search | Menu | Sign in || orig:  | Settings | Sign in'.

Suspected cause: The YouTube adapter's top() adds Settings (src/content/adapters/youtube.ts ~line 116), but the /playlist route seems to fall back to the generic extractor, which keeps Sign in and not the top bar's Settings menu button. Lead: give /playlist pages the adapter's header (top() and settingsMenu()).

Skeptic: Reproduced in 2 of 2 loads (15 s and 25 s waits). On /playlist?list=PL2MI040U_GXobmpXtTwBF7oHBGT5BETSD, Sift's header is 'Search | Menu | Sign in'. The original's masthead shows a visible 'Settings | Sign in'. Sift's Menu has only 'Close | Home | Shorts | You'. In the same session, home's header is 'Search | Menu | Sign in | Settings'. So on this page Settings (Appearance, Display language, Restricted Mode, Location) cannot be reached in Sift. The cause is in the code. youtube.extract in src/content/adapters/youtube.ts only routes /watch, /results, /shorts/, / and /feed/. /playlist returns null and falls back to the generic extractor, which never calls top() or settingsMenu(). This is a lost control on a secondary page, at the low end of medium. Screenshot: /home/nico/projects/sift-test-1/research/shots/skeptic-playlist-header.png

Skeptic's fix lead: In src/content/adapters/youtube.ts, give /playlist (and other routes that fall back, such as channel pages) the adapter's header: build the page with the adapter, reusing top() and settingsMenu(). Or add an optional Adapter hook (for example extraActions) in src/content/adapters/index.ts that index.ts merges into the generic page's header for youtube.

## F1062 (medium): English home: an English title gets a Persian one-line description ('Vector VS Thanos' -> 'Vector در برابر Thanos')

Found by: T1-youtube. Where: https://www.youtube.com/ with the page in English (lang=en), home list one-liners

Evidence: After the reset to hl=en (document lang 'en'), the home list showed the entry by TortillaDelta13 in two loads: once in tabwalk.ts at about 6 s, and once after a 40 s wait in eswatch.ts. Its link text was 'Vector در برابر Thanos', and its title attribute and the original's title are 'Vector VS Thanos' (English). The same batch had several Persian titles. Some got English lines ('Changes in Samsung One UI 9', 'Dariush Hormoz music about God, at 432 Hz'). This video's line came out in Persian. The Spanish home in the same session gave 'Vector contra Thanos'. A search for the video gives an English line ('Vector from Despicable Me appears in Avengers: Endgame to get revenge on Thanos'), so the bad line depends on the home batch. The line was made in this session: chrome.sh reinstalled the extension at start, which wipes the cache. On the next home load the video was no longer in the feed, so I have no screenshot.

Repro: cd /home/nico/projects/sift-test-1; SIFT_PORT=9461 SIFT_TAB=T1-youtube bun scripts/act.ts "goto:https://www.youtube.com/?persist_hl=1&hl=en" wait:5000; then SIFT_PORT=9461 SIFT_TAB=T1-youtube SEC=none W=40 bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/t1r10/eswatch.ts https://www.youtube.com/ prints each entry as 'line [original title] | meta'. Look for a line in Arabic script whose original title is English. The feed is personalized, so the exact video may differ.

Suspected cause: doLines now sends the page language ('en') for every 'about' list (the F821 fix). The slow fallback model still wrote this line in the batch's dominant Persian. vetLine's scriptFits(text, 'latin') accepts it because the kept names (Vector, Thanos) make 12 of 19 letters Latin, which is at least 0.5. Lead: for a known page language, reject a line that uses a script that is neither the page's nor in its title (here Arabic script in a line for a Latin-only title), and retry or keep the title.

Skeptic: Confirmed by the cache and by running the check code. Sift's IndexedDB cache ('sift'/'kv', read-only scan from the Options page) holds {"v":"Vector در برابر Thanos","ts":1793068551589}, saved at 02:35:51 UTC today, right after the 02:34 reinstall. New lines are saved only after lineFits passes (src/background/index.ts around line 571), so this Persian line passed the language check. I ran scriptFits, langScript and entryLang from src/background/text.ts on that line with want 'en' and title 'Vector VS Thanos'. scriptOf gives 'latin' (12 Latin letters to 7 Arabic-script ones), so scriptFits passes. entryLang then returns 'en' whatever detectLanguage says (reliable fa 90%, unreliable fa 60%, en, or null). The script matches the page, and fa has no FUNCTION_WORDS entry, so it falls back to the page language. lineFits therefore accepts it every time. I could not see it on screen: my English home load (40 s) gave English lines for every Latin title, and this video was not in the feed. Intermittent, because it depends on the model, but it breaks 'keeps the page's language', and the gap in the check is deterministic.

Skeptic's fix lead: In lineFits (src/background/index.ts ~line 684), or in a helper in src/background/text.ts, reject a line that has letters in a script that is neither the wanted language's script nor present in the title (here Arabic-script letters in a line for a Latin-only title). Also, in entryLang with output=true, when detection reliably names a language whose script differs from the text's main script and the page's, do not fall back to the page language.
