## F1030 (high): Lobsters comment threads: each comment becomes an AI one-line 'headline' cut at 200 characters, its text is deleted, and its title links to /login or to a URL quoted in it

Found by: R1-extractor. Where: src/content/extract/generic.ts:340-358 (Out.rewriteIfLong) with toItem's title fallback at generic.ts:2960 and 2977 (textLines first line, cut to 197+…)

Evidence: Harness on live https://lobste.rs/s/olnqh2/websites_should_be_printable (and the same HTML replayed offline): the comments are 'items [oneliner] ai=news'. The first comment is 2679 characters on the page. Sift's item title is the first 197 characters + '…'. The item has no text and no body, and its closing sentence ('very easy to cause trouble with them') appears 0 times in the outline. The 'I... don't even have a printer' comment links to /login (the upvote arrow a.upvoter href=/login, text '~'). The first comment links to /TR/using-aria/#rule1, a URL quoted inside it. A comment also gets the meta '6 comments'. The replies that round 9 now nests under each comment have the same form. pre-round-9 (p9m.js) gives the same items, so this is not a regression. Not checked in the real extension, to avoid AI line calls. It runs the same extract().

Repro: cd /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9 && bun run.ts r10m.js,p9m.js https://lobste.rs/s/olnqh2/websites_should_be_printable 1 --wait 2500 | grep -n 'items\|^  \*' ; offline: bun run.ts r10m.js /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r10/dl/lob.html 1 --as https://lobste.rs/s/olnqh2/websites_should_be_printable

Suspected cause: Lobsters comments have no heading, and div.comment_text matches no POST_BODY. So toItem names each comment by its first text line (cut at 200) and takes a link inside it (the upvoter or a quoted URL) as its target. Out.rewriteIfLong then sees 4 or more entries averaging over 13 title words, marks the block oneliner/news, moves each entry's text into AI context, and sets it.text = undefined. Lead: never rewrite entries whose title came from textLines (not a heading or a naming link), or entries in a comments area. Treat comment_text/comment-body/comment-content as the post body, and never take a vote link as an entry's target.

Skeptic: I reproduced the outcome, but the claimed cause is wrong. I ran a bundle built fresh from sift-test-8 src on live https://lobste.rs/s/olnqh2/websites_should_be_printable. The comment block is 'items [oneliner] ai=news'. The first comment's title is 198 characters (197 plus the ellipsis). It has text=undefined, context=undefined and no body, so roughly 2,400 characters of that comment never show. Replies have the same form. Titles link to /login, or to a URL quoted in the comment (w3.org/TR/using-aria/#rule1). p9m.js gives the same result, so this is not a regression. Real cause, found with instrumentation: Lobsters marks every comment's text as <div role="heading" aria-level="3" class="comment_text">. toItem therefore takes the whole comment as the heading: title = textIn(heading), cut at 197. The text walk then skips every text node with 'heading?.contains(own) continue' (48 nodes skipped for the first comment). The text is never collected, so rewriteIfLong does not delete it, and textLines is not used. ctx.inComments is false here. When the heading has no link, the named-link fallback picks the upvoter arrow (a.upvoter, href=/login, text '~' or '31') as main. rewriteIfLong then marks the top-level list as oneliner/news, so each top-level comment's 197 characters are replaced by an AI headline. Nested replies (it.replies) render without rewrite and keep the cut title. This is a real loss of content on a major discussion site, so high or medium severity. The site's ARIA misuse does not excuse Sift, because the spec says Sift works on any site.

Skeptic's fix lead: In generic.ts toItem, around line 2907, do not accept a [role=heading] that is not h1-h6 as the entry's heading when it holds block content (more than one <p>, a <ul>, or text over about 200 characters). Treat it as the post body instead, so bodyEl/postBodyOf reads the comment in full. Also treat .comment_text as a POST_BODY so the comments area is detected (ctx.inComments). In the named-link filter around line 2928, exclude voteLink(a) so an upvote arrow is never main. In Out.rewriteIfLong (line 342), skip blocks whose entries have a body, or whose title came from a heading that holds paragraphs.

Repro: SIFT_PORT=9468 SIFT_TAB=R1-extractor bun scripts/visit.ts http://127.0.0.1:8799/fx/r10rev-checkout-frame.html co --wait 6000 (and r10rev-cafe-map.html); harness: cd /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9 && bun run.ts r10m.js,p9m.js http://127.0.0.1:8799/fx/r10rev-checkout-frame.html 1

Skeptic: Reproduced in the harness and in the real extension on port 9468, with the same result both times. In the code, routeFirst (generic.ts:7742) fires on any tool portal within 5 blocks after any table of 6 or more rows, whenever any form comes earlier. Nothing checks for a route. A contact form, an hours table and a map is a common small-business layout.

Skeptic's fix lead: In routeFirst (generic.ts:7742-7771), require a real route before moving anything. The form should have two place fields (from/to or origin/destination), or the table head or summary should match distance and time ('Distance', 'km', 'mi', 'Time', 'h:mm'), or the rows should read as turn steps. ## F1033 (medium, regression): 'Copy link' is now an action on every feed entry (The Verge home: 17), copying the entry's own address that its title link already gives

Found by: R1-extractor. Where: src/content/extract/generic.ts:924 (usefulControl COPY_LABEL, ctrl12 F904), reached from toItem's button loop at generic.ts:3216

Evidence: Harness, live https://www.theverge.com/: 0 'Copy link' before round 9, 17 now, one '{Copy link}' per quick-post entry ('X has another new head of product.', 'Today's Vergecast: Files are over…', 'Proton To Re-Interview Staff…'). Real extension (9468): 17 Copy link buttons inside Sift's list entries. On the page each is <button aria-label="Copy link"> in div.duet--content-cards--quick-post with obfuscated classes, so shareTarget() does not see a share bar.

Repro: cd /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r9 && bun run.ts r10m.js,p9m.js https://www.theverge.com/ 1 --wait 3000 | grep -c 'Copy link'

Suspected cause: COPY_LABEL returns true before SKIP_LABEL/SHARE_LABEL for any 'Copy link' that is not in a share bar or an article. Inside a list entry it copies the entry's own link. Lead: in toItem, skip a 'Copy link' button when the entry has its own target (main). Keep it on app pages and in dialogs (F904's shared-folder case).

Skeptic: Reproduced. In the harness on live theverge.com there are 17 'Copy link' actions now and 0 with p9m.js. In the real extension on port 9468, Sift's view has 17 Copy link buttons, all inside li.item entries ('X has another new head of product.', 'Today's Vergecast…', 'Proton To Re-Interview…'). Each of those entries already has a title link to the same post, so the button repeats the link. That adds 17 tab stops of share-type clutter that the README says Sift removes. In the code, COPY_LABEL at generic.ts:924 returns true for any 'Copy link' that is outside a share bar and outside ctx.inArticle, and toItem's button loop (around line 3216) adds it to each entry.

Skeptic's fix lead: In toItem's button loop (generic.ts around line 3216), skip a button whose label matches COPY_LABEL with link/enlace when the entry has its own target (main or href). Alternatively, in usefulControl (line 924), return false for 'Copy link' inside a list entry (rowOf(ref) or an item context) unless ctx.inDialog or the page is an app page. This keeps F904's shared-folder case.

## F1046 (medium): MoinMoin wiki page: H1 is the last section heading ('More information'), and the site header fills the top of the content

Found by: T4-generic. Where: https://wiki.debian.org/SourcesList

Evidence: The original's first heading is h1#locationline 'SourcesList'. The page's sections also use h1 ('Introduction', 'Using APT sources', ..., the last one 'More information'). Sift's H1 is 'More information', and 'SourcesList' only appears later as an H2 link. Above it, main starts with the site header: Debian, Wiki, Login, 'Search:' field with Titles/Text buttons, Login, Info, Attachments, and a 'More Actions:' select. That is 10 tab stops (tabwalk) before the page title, and Sift's bar has only 'wiki.debian.org'. Screen reader users hear 'More information' as the page title. Shot: /home/nico/projects/sift-test-4/research/shots/r10t4-debwiki.png

Repro: SIFT_PORT=9464 SIFT_TAB=T4-generic bun scripts/act.ts goto:https://wiki.debian.org/SourcesList wait:8000 'eval:[document.querySelector("sift-root").shadowRoot.querySelector("main h1").innerText, document.querySelector("h1").innerText]' prints ['More information','SourcesList']; bun scripts/tabwalk.ts https://wiki.debian.org/SourcesList 12 shows Debian, Wiki, Login, input, Titles, Text, Login, Info, Attachments, select before 'SourcesList'.

Suspected cause: With several h1s, the title pick takes the last or the deepest-in-content h1 instead of the first visible one, or the one that matches document.title ('SourcesList - Debian Wiki'). The MoinMoin #header (search form, nav, page actions) is not recognized as site chrome, so it is not moved to the bar or the Menu.

Skeptic: Partly reproduced on the claimed page, fully on another page of the same wiki. On wiki.debian.org/SourcesList I now get H1 'SourcesList' at 3 s, 8 s and 30 s (cached Short version), in two runs and after 'Show full text'. T4's saved outline (r10t4-debwiki.txt) shows H1 'More information' during the first, SHORTENING load. On wiki.debian.org/Backports (5 h1s, uncached) the bug holds in every state and on reload. Sift's H1 is 'External links', the last section h1, at y=77. 'Backports' (h1#locationline > ul > li > a[href=/Backports]) becomes an H2 link at y=591. The site-header part reproduces on SourcesList: tabwalk goes Skip to content, Debian, Wiki, Login, input, Titles, Text, Login, Info, Attachments, select, then SourcesList. Likely cause, from reading the code: docTitle() splits 'Backports - Debian Wiki' and keeps both parts. The site name falls back to the hostname, normalized to 'wiki debian', which does not match 'Debian Wiki' because the word order differs. docTitle then returns the longest part, 'Debian Wiki'. No h1 matches, so titleH1() falls back to the last h1 before or inside the article. On SourcesList, 'SourcesList' and 'Debian Wiki' are both 11 characters, so the tie and the stable sort keep the right one, which explains why it passes there now.

Skeptic's fix lead: src/content/extract/generic.ts docTitle(): treat a <title> part as the site name when its words match the site or host words as a set ('Debian Wiki' vs wiki.debian.org). titleH1(): with no title match and several h1s, prefer the first plain h1 (or the one matching the URL's last path segment) over the last one before the article. Separately, the MoinMoin #header (search form, page actions, More Actions select) should go to the bar or Menu, not the top of main.

## F1047 (medium): Government service page shows a 2021 first-publish date under the H1 that the page never shows (updated 2026)

Found by: T4-generic. Where: https://www.argentina.gob.ar/servicio/tramitar-el-pasaporte

Evidence: Sift's line after the H1 'Tramitar el Pasaporte' is '15 mar 2021'. The original's text contains no '2021' anywhere. The date comes from <meta property=article:published_time content=2021-03-15T10:47:41-03:00>. The same page has article:modified_time and og:updated_time 2026-03-06. So a reader is told this passport procedure is from 2021 when it was updated this year. This is the same kind of error as F957, which is now fixed for GOV.UK's JSON-LD (the renew guide shows no 2012 date), but here it comes from the meta tag. Shot: /home/nico/projects/sift-test-4/research/shots/r10t4-arg-servicio.png

Repro: SIFT_PORT=9464 SIFT_TAB=T4-generic bun scripts/act.ts goto:https://www.argentina.gob.ar/servicio/tramitar-el-pasaporte wait:8000 'eval:[document.querySelector("sift-root").shadowRoot.querySelector("main h1 + *")?.innerText, /2021/.test(document.body.innerText), document.querySelector("meta[property=\"article:modified_time\"]")?.content]' prints ['15 mar 2021', false, '2026-03-06T10:16:18-03:00'].

Suspected cause: byline() in src/content/extract/generic.ts takes meta article:published_time when the page shows no date. The F957 fix appears to cover only the JSON-LD fallback. The meta date should be shown only if the page shows it, or the newer article:modified_time should be preferred when it exists.

Skeptic: Reproduced. On argentina.gob.ar/servicio/tramitar-el-pasaporte, the line after Sift's H1 'Tramitar el Pasaporte' is '15 mar 2021'. With Sift off, the original's text (4272 chars) has no year at all and no <time> or [datetime] elements. The date comes from meta article:published_time 2021-03-15. article:modified_time and og:updated_time are both 2026-03-06. In byline() in src/content/extract/generic.ts, `when` takes meta article:published_time / name=date / itemprop=datePublished with no check that the page shows the date. The F957 rule ('never a date the page does not show') was added only on the ldDate path. Telling readers a passport procedure dates from 2021 when it was updated this year is misleading, so medium.

Skeptic's fix lead: src/content/extract/generic.ts byline(): apply the F957 rule to the meta path too. Use article:published_time (or name=date or datePublished) only when the page shows that date, for example in a <time> or as text near the title. Otherwise prefer article:modified_time / og:updated_time, or show no date, as ldDate already does.
