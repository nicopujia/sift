## F1040 (high): 'Copy link' / 'Copy' buttons that copy with document.execCommand (clipboard.js, copy-to-clipboard) copy nothing in Sift, while the page says 'Link copied'

Found by: R2-interaction. Where: src/content/shield.ts:48 (no portals: the whole <body> is made inert) with src/content/index.ts:3319 (H.act replays the click with the page still inert)

Evidence: New fixture http://127.0.0.1:8799/fx/r10int-copylink.html. Its Copy link button copies the way clipboard.js does: a read-only textarea appended to <body>, select(), execCommand('copy'), then removed. ?lib=c2c copies the way the copy-to-clipboard package does (a span in <body>, a range, execCommand). Clipboard seeded with 'BEFORE', read back through CDP permissions. Original: clipboard = the event URL, copy-event selection = the URL, the fake textarea is focused. Sift: execCommand returns true, the copy event fires with selection "", the textarea is not focused, and the clipboard stays 'BEFORE'. The page still shows 'Link copied', and ?lib=c2c behaves the same. Control 1: ?api=1 (navigator.clipboard.writeText) copies correctly in Sift. Control 2: ?portal=1 adds a shown iframe, so body is not inert as a whole (document.body.inert false). Both execCommand patterns then copy correctly in Sift, which isolates the cause: an element the page appends to an inert <body> cannot take focus or a selection during the click. Before round 9 these buttons were dropped (F904), so the button is new, but it fails silently with a false 'copied' message. GitHub's Copy path and Docusaurus' code Copy use navigator.clipboard and work.

Repro: No test Chrome running needed beyond: SIFT_PORT=9467 ./scripts/chrome.sh start; cd /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r10int; SIFT_PORT=9467 SIFT_TAB=R2-interaction bun copy.ts prints SIFT {..."execCommand true, fake focused=false"..., msg 'Link copied', clipboard 'BEFORE'}. Then: 'bun copy.ts orig' (clipboard = URL), 'bun copy.ts sift "?lib=c2c"' (BEFORE), 'bun copy.ts sift "?portal=1"' (URL).

Suspected cause: With no exceptions, shield.ts desired() adds document.body itself to the inert set, so anything the page appends to body during Sift's replayed click is inert. When portals exist, only body's children are inert, and a new child stays usable until the next refreshShield. Lead: make body's children inert instead of body, as the exceptions path already does, or replay H.act clicks inside withoutShield(…, el).

Skeptic: Confirmed, high severity: execCommand-based Copy buttons copy nothing in Sift but still say 'Link copied'. I ran the reporter's fixture /fx/r10int-copylink.html. In Sift, the copy event fired with selection "", the active element was sift-root, the fake textarea was not focused, and the clipboard stayed 'BEFORE'. On the original, the clipboard got the URL. '?lib=c2c' behaved the same in Sift (still BEFORE). The controls held: '?portal=1' copied the URL in Sift, and '?api=1' (navigator.clipboard) copied it too. To rule out the fixture being unfaithful, I wrote /home/nico/projects/sift/research/fixtures/r10skep-clipboardjs.html, which loads the real clipboard.js 2.0.11 from cdnjs. In Sift, two runs gave the same result: selection "", the library fired 'success', the page showed 'Link copied', and the clipboard stayed BEFORE. On the original, the clipboard got the URL. The code matches the stated cause. With no portals, shield.ts desired() (line 47-49) marks document.body itself inert. H.act (index.ts ~3317) calls proxy.click(el) with no withoutShield, because proxy.click only lifts the shield when opts.focus is set. So the textarea or span the page appends to body during the click is inert and cannot hold a selection.

Skeptic's fix lead: In H.act (src/content/index.ts, the go() closure), replay the click with the shield lifted for that element: withoutShield(() => proxy.click(el), el), imported from shield.ts. Then put focus back on Sift's control, as proxy.click's focus path does, so a page that moves focus during the click does not take it from Sift. The alternative is shield.ts desired(): when there are no exceptions, mark body's children instead of body, so a node appended to body during the click stays usable until the next refreshShield.

## F1041 (medium): Typed digits on a React Aria-style date or time field (contenteditable role=spinbutton) do nothing in Sift; only the arrow keys work

Found by: R2-interaction. Where: src/content/index.ts:970-975 (sliderKey sends digits to a page spinbutton only as keydown/keyup through proxy.key)

Evidence: New fixture http://127.0.0.1:8799/fx/r10int-datesegs.html: a date as three contenteditable role=spinbutton segments that take arrows on keydown and digits on beforeinput (insertText). That is how @react-aria/datepicker useDateSegment works: I checked its source, where useEvent(ref,'beforeinput') calls onInput(e.data) and keydown handles only Backspace/Delete. Original: click the month, type '7', and month = 7. ArrowUp then gives 8. Sift: Sift shows span[role=spinbutton] 'mm'. Click it and type '7': month stays null and the log is []. ArrowUp sets 1. So a year or day can only be reached by repeated arrow presses. Pre-round-9 build (reverse-applied round9-fixes.diff, port 9497): the segments were textareas, and neither typing nor arrows reached the page. So this is not a regression; F902's 'typed digits' part is only half done.

Repro: cd /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r10int; SIFT_PORT=9467 SIFT_TAB=R2-interaction bun segs.ts prints 'after typing 7 month=null log=[]' then 'after ArrowUp month=1'. 'bun segs.ts orig' prints month=7, then 8.

Suspected cause: proxy.key dispatches keydown/keyup only, with no beforeinput or input carrying the digit. Lead: for a digit on a contenteditable spinbutton, also dispatch a cancelable InputEvent('beforeinput', {inputType:'insertText', data}) on the page element. If it is not cancelled, send the input event too.

Skeptic: Confirmed, medium severity. On the reporter's fixture I clicked Sift's month spinbutton and typed '7': month stayed null and the log was []. ArrowUp then set it to 1. On the original, '7' set month=7 and ArrowUp gave 8. I got the same result twice in Sift. A listener on the page segment showed that only keydown:7 and keyup:7 arrive, with no beforeinput or input. To check that the fixture is faithful, I downloaded @react-aria/datepicker 3.14.0's useDateSegment.mjs from jsDelivr. The reporter's saved copy is an empty 'Not found' file. Its onKeyDown handles only Backspace/Delete (and Ctrl/Cmd+A), and typed characters go through useEvent(ref,'beforeinput') to onInput(e.data). I also built /home/nico/projects/sift/research/fixtures/r10skep-ariadate.html with a real react-aria-components DateField from esm.sh. On the original, typing 7 set month 7/7. In Sift, two runs left month at mm/null after typing 7, and ArrowUp set it to 10. Sift also labels these spinbuttons 'Empty'. The cause is in src/content/index.ts sliderKey (~970-978): digits reach the page spinbutton only through proxy.key, which sends keydown/keyup and nothing else.

Skeptic's fix lead: In sliderKey (src/content/index.ts), for a digit on a page spinbutton: when proxy.key's keydown was not cancelled, also dispatch new InputEvent('beforeinput', {inputType:'insertText', data:e.key, bubbles:true, cancelable:true}) on el. If that is not cancelled, follow it with an 'input' event. Backspace/Delete can keep the keydown path, since React Aria handles them on keydown.

## F1042 (medium): Each arrow key on Sift's copy of a page slider or spinbutton forces up to three full re-reads of the page, so holding a key on a long results page lags far behind the original

Found by: R2-interaction. Where: src/content/index.ts:976-977 (sliderKey calls afterAct per key) with src/content/index.ts:3059-3063 (afterAct schedules schedule(0) at 60, 400 and 1200 ms)

Evidence: New fixture http://127.0.0.1:8799/fx/r10int-priceslider.html: a role=slider price filter above 1500 stays. In 20 ArrowRight presses at about 30 per second, Sift ran 28 full extractions (87 ms each), and the presses took 2446 ms to get through, against 1027 ms on the original (0 extractions). On fx/r10int-datesegs.html?big=3000 (spinbutton, new in round 9), 20 ArrowUp presses took 8654 ms against 1192 ms on the original, with 20 extractions of about 725 ms. The machine was loaded (load average about 21), so absolute times are inflated, but the ratio is one forced extraction per key. Pre-round-9 build: 33 extractions for the same 20 slider keys, so this is old for sliders and now also applies to spinbuttons.

Repro: cd /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r10int; SIFT_PORT=9467 SIFT_TAB=R2-interaction bun slidelag.ts sift 1500 then bun slidelag.ts orig 1500 (compare keysMs and extractions). For the spinbutton: bun spinlag.ts sift 3000 and bun spinlag.ts orig 3000.

Suspected cause: afterAct is meant for one action, but a held key is many. Each press queues three schedule(0) calls, which skip the idle wait and the back-off, so a key repeat becomes a run of back-to-back extractions. Lead: in sliderKey, coalesce. Schedule one trailing schedule(0) about 300 ms after the last key (reset on each key) instead of afterAct per key, and set actAt/actedAt only.

Skeptic: Confirmed, medium severity. The machine was loaded (load average about 14 on 6 cores), so absolute times are inflated. On /fx/r10int-priceslider.html?big=1500, 20 ArrowRight presses on Sift's range copy took 2779 ms and 3641 ms over two runs, with 26 and 23 extractions. The original took 856 and 878 ms, with 0 extractions. On /fx/r10int-datesegs.html?big=3000, 20 ArrowUp presses took 6895 ms and 15861 ms in Sift (24 extractions each), against 1331 ms on the original. I isolated the cause with my own control. In Sift mode, page script sent the same 20 keydowns to the page slider, so the page mutated identically but Sift's key path did not run. That gave 1 extraction and 884-989 ms. So the extra runs come from Sift's key path, not from the page's changes. The code matches: sliderKey calls afterAct() on every key, and afterAct queues schedule(0) at 60, 400 and 1200 ms. schedule(0) skips the idle wait and back-off, and run() has no back-to-back guard. The lag only matters on long pages, where one extraction costs about 100 ms or more, but there each held arrow key costs about one full extraction.

Skeptic's fix lead: In sliderKey (src/content/index.ts ~976-977), stop calling afterAct per key. Set store.actAt and actedAt, and keep one trailing timer, reset on each key (clearTimeout plus setTimeout of about 300 ms), that calls schedule(0) once, maybe with one later schedule(0) for slow page answers. Consider the same coalescing in slideTo if it calls afterAct per step.

## F1043 (high): Recipe card 'Jump to Recipe' does nothing in Sift (Tasty Recipes jump target is an empty span)

Found by: T4-generic. Where: https://pinchofyum.com/the-best-soft-chocolate-chip-cookies (any Tasty Recipes blog)

Evidence: Clicking Sift's 'Jump to Recipe' link (href #tasty-recipes-39213-jump-target) leaves Sift's view where it was: focus stays on the link at y=282 and the URL gets no hash. The click is replayed on the original, which jumps: its scrollY becomes 15635. The target is <span class=tasty-recipes-jump-target id=tasty-recipes-39213-jump-target> with no content, followed by an ad div and then the recipe card, so Sift has no element to go to. Other in-page links on the same page work because their targets are headings: '#watch' goes to h2 'Prefer To Watch Instead Of Read?' at y=71, '#faq' to its h2, '#comments' to h3 '4371 Comments', and '#respond' to h3 'Leave a Reply'.

Repro: SIFT_PORT=9464 SIFT_TAB=T4-generic bun scripts/act.ts goto:https://pinchofyum.com/the-best-soft-chocolate-chip-cookies wait:9000 'click:Jump to Recipe' wait:3000 'eval:(()=>{const r=document.querySelector("sift-root").shadowRoot;const a=r.activeElement;return [a&&a.innerText,a&&Math.round(a.getBoundingClientRect().top),scrollY]})()' prints ['Jump to Recipe',282,15635]: Sift did not move, but the original scrolled to the recipe.

Suspected cause: The in-page link handler focuses the Sift element mapped to the target id. An empty span (display:block, no text) is not rendered, so nothing is found. It could fall back to the next rendered element after the target (here, the recipe card's h2 'The Best Soft Chocolate Chip Cookies').

Skeptic: Reproduced twice on pinchofyum. Sift's 'Jump to Recipe' link (href ...#tasty-recipes-39213-jump-target) is at y=282 before and after the click. Focus stays on the link, the host's scrollTop stays 0, location.hash stays empty, and the original's scrollY goes to 15635. The recipe card is in Sift: h2 'The Best Soft Chocolate Chip Cookies' at y=14116 and Ingredients at 14485, so there is a place to go. Other in-page links do work: clicking the 'Chocolate Chip Cookies: Frequently Asked Questions' link focuses that h2 at y=72. The target is <span class=tasty-recipes-jump-target style=display:block> with no content, a direct child of div.entry-content. In Sift's main only headings and one details element carry data-key. Inference: in showPlace(), the loose pick takes found.around (the article block that holds the span) before found.after. That block has no data-key element in the shadow DOM, so showPlace returns without scrolling or focusing. Also, found.after is the first match in Sift's order, not DOM order: 'Featured comment' sits early in Sift but late in the DOM.

Skeptic's fix lead: src/content/index.ts showPlace(): when found.inside is empty and the target has no rendered text (an empty jump-target span), use the nearest block after the target in document order (here the recipe h2 'h:r2l') before found.around. Pick found.after by DOM position, not by Sift's walk order. If the chosen block has no [data-key] element, fall back to the next block that has one instead of returning silently.

## F1045 (medium): Recipe ingredients are shown twice, partly split over several lines, and disagree after switching units

Found by: T4-generic. Where: https://pinchofyum.com/the-best-soft-chocolate-chip-cookies, Ingredients (Tasty Recipes plugin, used by many food blogs)

Evidence: Each ingredient in the original is <input type=checkbox aria-label='8 tablespoons of salted butter'><label for=...></label> (empty label) followed by the visible text. Sift shows a checkbox labeled with the aria-label AND the visible text again on the next line, so the list doubles in length. Some lines are also split: '1 teaspoon' / 'vanilla', '1' / 'egg', '1 1/2' / 'cups' / 'all purpose flour' / '(6.75 ounces)'. After clicking 'M' (metric; it works: M aria-pressed=true), the checkbox labels still say '1/2 cup white sugar' and '1/4 cup packed light brown sugar', right above '100 grams white sugar' and '50 grams packed light brown sugar'. The original shows each ingredient once, on one line. Shots: /home/nico/projects/sift-test-4/research/shots/r10t4-pinch-ingr.png, /home/nico/projects/sift-test-4/research/shots/r10t4-pinch-metric.png

Skeptic's fix lead: src/content/extract/generic.ts list item walk (list(), labelOf() and the checkbox rendering): when a checkbox's own <label> is empty and its li holds visible text, render one checkbox labeled by the li's live visible text (kept as one inline run), not the aria-label plus separate paragraphs for each span.
