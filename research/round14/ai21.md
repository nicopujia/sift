## F1402 (medium): English home: a foreign title still shows with no English line when the model answers in the title's language (F1231 remainder)

Found by: T1-youtube. Where: https://www.youtube.com/ (English), home list one-liners; src/background/index.ts doLines (lineFits failure path)

Evidence: In each 24-entry English home load, 1 to 2 Persian entries kept only their Persian title, for example 'ازدواجی وحشتناک در گیلان 😨 که بعد از شنیدن داستانش تا چند روز خوابم نبرد'. The captured model reply for it (request lang 'en', gpt fallback) was Persian: 'ازدواج وحشتناک در گیلان و داستان آن'. lineFits rightly dropped it, and Sift stored '\0keep-title' with a 1-day expiry, without asking another model. 'بررسی آپدیت جدید سامسونگ One UI 9' had the same keep-title. Nothing is lost against the original, but these entries miss the one-line description in the page's language. The 1-day expiry means a later visit retries.

The feed is personalized, so the titles vary.

Suspected cause: doLines: when lineFits rejects a line for its language, keepTitle(m, DAY) is saved without retrying the next model in the chain, or the same model with a firmer language instruction.

Skeptic: Reproduced live and by mock. This is the same defect as the F1231 remainder, so track it once. Live: the current English home feed had no Persian titles, and 2 direct requests (4 Persian titles, lang en, gpt-6-luna) all came back in English. An English YouTube search with Persian results did reproduce it: results?search_query='بررسی آپدیت سامسونگ' (page lang en). Sift showed 9 of about 22 Persian rows with only the Persian title. After deleting their keep-title entries and capturing the worker's model calls (aicap.ts), the model answered in Persian for 8 entries. Most of them had long Persian description text in their context. Examples: 'بررسی تغییرات و قابلیت‌های جدید آپدیت One UI 9 سامسونگ' and '۱۰ ویژگی سامسونگ برای استفاده از قابلیت‌های گوشی'. No other model was asked for them. Sift then showed 'بررسی آپدیت جدید سامسونگ One UI 9' and 'بررسی آپدیت One UI 9 سامسونگ؛ …' with no English line. The cache held '\0keep-title' with exp = ts + 24 h. Mock: I replaced the worker's fetch so every model call answers in Persian, then sent one lang 'en' item. Result: one model call (openai/gpt-6-luna), reply {done:true} with no line, and keep-title cached for 24 h. In code (src/background/index.ts emit in doLines), done.add(id) runs before lineFits. On failure, keepTitle(m, DAY) runs, so the entry is never in r.left and never retried. Nothing is lost against the original, so medium at the low end. Side note, not claimed: one cached line was itself Persian ('تغییرات آپدیت Samsung One UI 6.0', about half Latin letters) and was shown on the English page, so lineFits let a mixed-script wrong-language line through.

Skeptic's fix lead: src/background/index.ts doLines/ask emit: when lineFits fails on language, do not keepTitle at once. Collect the entry and re-ask once, either with the language spelled out (langName(want), e.g. 'English', and a note to ignore the context's language) or with the next model in the chain. Call keepTitle(m, DAY) only if that retry also fails. Optionally pass the language name, not just the 'en' code, in the per-item input and LINES_SYSTEM. Also tighten lineFits/scriptFits so a line whose non-Latin letters are in the title's script does not pass for 'en'.

## F1408 (medium, regression): GitHub issue #4416 no longer gets a Short version: works.md 110's 'Show full text' toggle is gone

Found by: T3-tools. Where: https://github.com/preactjs/preact/issues/4416

Evidence: Two loads, 75 s each: no 'Shortening…' tag and no 'Show full text' or 'Show short version' button. In the same session the AI worked elsewhere: Wikipedia Bread got its Short version at 20.8 s and es Pan at 49.4 s. Nothing is lost: 12/12 comment bodies, 3/3 code blocks and 6/6 blockquotes match. Round 12's outline (/home/nico/projects/sift-test-3/research/shots/skeptic-gh4416.txt, Oct 26) had '[button] Show full text' right after 'p: Open / #4419', with only the issue body condensed. Today's outline starts 'H1 … #4416 / New issue / [button] Copy link / p: Issue Open / #4419 / trusktr / on Jun 20, 2024', then the full body. Sift's main now has a single article of about 1583 words that holds the body and every comment, with 12 'Actions for X's comment' buttons and reaction buttons.

Repro: cd /home/nico/projects/sift-test-3; SIFT_PORT=9463 ./scripts/chrome.sh start; SIFT_PORT=9463 SIFT_TAB=T3-tools bun scripts/visit.ts https://github.com/preactjs/preact/issues/4416 gh4416 --wait 75000. Then: bun scripts/act.ts "eval:[...document.querySelector('sift-root').shadowRoot.querySelectorAll('button')].map(b=>b.innerText).filter(t=>/full text|short version/i.test(t)).join('|')" prints an empty string. Compare research/shots/gh4416.txt with research/shots/skeptic-gh4416.txt.

Suspected cause: GitHub's issue header changed: there is a new 'Copy link' button and the header now reads 'Issue Open'. The issue body is probably no longer extracted as its own article, so the whole thread is one article. proseArticle() in src/content/extract/generic.ts then rejects it: there are about 14 actions, more than 6 + prose/1500. I could not check whether Sift's code also played a part. The round 12 diff does not touch proseArticle.

Skeptic: Reproduced, but it is not a Sift regression. Sift's code is not the trigger: GitHub's new issue layout is. One live load with a 75 s wait (visit.ts skv-gh4416) shows no 'Show full text', 'Show short version' or 'Shortening' button. Sift's main holds one article of 1583 words with 13 buttons, and its outline starts 'H1 … #4416 / New issue / [button] Copy link / p: Issue Open', as claimed. To find the cause, I bundled the extractor from the current src (scratchpad skn1/skx.js). I also bundled it from round 11, commit 7bd95ba, the code that was live when works.md 110's toggle was confirmed (skx11.js, made with git archive). I ran both on today's live page with Sift off. Both pick the same element, div.contentArea (9604 characters: the issue container plus the comment timeline). Both give the same article: 461 words, prose=false, blocks ul/p/pre/form/items. findArticle, proseArticle and their helpers are byte-identical from round 11 to now. So the change came from GitHub's DOM. The exact cause is narrower than the claim's action count. That article is non-prose only because the reactions pill ('👍 2 reactions', a checkbox field) makes a form with fields. Without the form block, proseArticle returns true. The issue body alone (23 blocks) is also prose=true. The body sits in [data-testid=issue-body] > div > [data-testid=issue-viewer-issue-container] > div.contentArea, and findArticle climbs to contentArea. Nothing is lost: all text is shown in full. Severity is low to medium. Re-file it as an adaptation to GitHub's new layout, not a regression.

Skeptic's fix lead: In src/content/extract/generic.ts findArticle(), in the climb loop (around 3880-3910), stop at an ancestor whose extra prose is a comment timeline. Here that means stopping at [data-testid=issue-viewer-issue-container]: its parent's other child holds the comments, which postGroup does not recognize. In proseArticle() (around 5746), do not set fields for a form made only of toggle checkboxes with no text field or submit, such as reaction pills ('N reactions').
