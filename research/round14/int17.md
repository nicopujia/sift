## F1412 (high): Rename in place fails when clicked more than about 3 s after load: Sift's focus lands on the next button ('Invite people'), so typing the new name opens the invite popup instead

Found by: T5-amazon-gmail-a11y. Where: fx/r11int-focusclose.html and fx/r12int-focusportal.html (the F1102 fixtures), Rename button, by mouse and by keyboard; src/content/index.ts followPageFocus (~3396) and the sift-focus listener (~3380)

Evidence: Load the page, then click Sift's 'Rename list: Groceries' about 5 s later. The page enters editing (log ['editing']), but Sift's focus stays on the clicked <button data-ref>, and that node re-renders as 'Invite people'. Typing ' and bread' then Tab gives log ['editing','share open'] and name 'Groceries', with Sift's share sheet open. The original, same timing: log ['editing','edit ended: Groceries and bread']. By keyboard (focus Rename, Enter, type XY, Tab): Sift's focus is on 'Invite people', the log is ['editing'], the name stays 'Groceries', and the page is left stuck in editing. If clicked 1.5-2.5 s after load it works: focusout 'Invite people', then focusin textarea at 28-43 ms. That window is why the round 12 recheck, which clicked at 2.5 s, passed. Fails in 2 of 2 runs at 5 s, 2 of 2 with a 1-2 s pause before the click, and 1 of 2 with a 300 ms pause. Shot: /home/nico/projects/sift-test-5/research/shots/r13t5-f1200-rename.png

Repro: SIFT_PORT=9465 ./scripts/chrome.sh start (in /home/nico/projects/sift-test-5); cd /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/r13t5c; SIFT_PORT=9465 SIFT_TAB=T5-amazon-gmail-a11y FX=http://127.0.0.1:8799/fx/r11int-focusclose.html LOADWAIT=5000 bun rn4.ts prints {"log":["editing","share open"],"name":"Groceries","sharebox":true,...}. With LOADWAIT=1500 the text reaches the name. Keyboard: bun go.ts goto:http://127.0.0.1:8799/fx/r11int-focusclose.html wait:5000 'sx:(Array.from(R.querySelectorAll("button")).find(b=>/Rename/.test(b.getAttribute("aria-label")||b.innerText)).focus(),1)' press:Enter wait:800 focus keys:XY press:Tab wait:800 log 'eval:document.getElementById("name").textContent' prints focus '… :: Invite people', log ["editing"], "Groceries". Original: bun go.ts goto:<same> wait:5000 press:Alt+Shift+S wait:800 'pclick:#name' 'keys: and bread' press:Tab log prints 'edit ended: Groceries and bread'.

Suspected cause: An inference from a focus trace and the code, not proven. The page's name.focus() during the replayed click fires sift-focus, which schedules followPageFocus with setTimeout(0). Later in the visit, the re-render for the page change has not run by then. So followPageFocus finds Sift's existing Rename <button> with the same data-ref, sees it already focused, and clears pageFocusTo. The next render turns that ref into a textarea. Preact reuses the old <button> node for the following control (Invite people), and focus stays on it. During boot the render runs first, so the follow finds the textarea. Lead: keep pageFocusTo for the next render when the matched control is not an editable field but the page element is now editable (contenteditable/input), or key controls by ref so a node is never reused for another control.

Skeptic: Reproduced on both fixtures, fx/r11int-focusclose.html and fx/r12int-focusportal.html, with my own script (scratchpad/skeptic-n0/rn.ts). Mouse click on Sift's 'Rename list: Groceries' 5 s after load, then typing ' and bread' and Tab: log ['editing','share open'], name 'Groceries', share box open. This failed in 3 of 3 runs on focusclose and 2 of 2 on focusportal. It also failed with a 3.5 s load wait. Keyboard (focus Rename, Enter, type XY, Tab) failed 2 of 2 on focusclose and 1 of 1 on focusportal. Sift's focus sits on 'Invite people', the log stays ['editing'], the name stays 'Groceries', and the page is left in editing. At 1.5 s and 2.5 s the text does reach the name. The original (Alt+Shift+S, click #name, same typing) gives ['editing','edit ended: Groceries and bread'] in 3 of 3 runs, so the difference comes from Sift, not the page. One part of the suspected cause is wrong. Preact does not reuse the node. My probe shows the focused Rename button [data-ref r8] is removed (isConnected false). Sift renders a textarea [data-ref r8] for the name. Focus then lands on a different node, the 'Invite people' button [ra]. Sift's window-capture focusin listener swallows that focusin. The move comes from paint() calling refocus(). twinOf() wants the same tag, so the textarea with the same ref does not count. The first 'near' control wins, which is 'Invite people'. The rest of the suspected cause matches the code. The setTimeout(0) followPageFocus already ran against the old Rename button. That button was focused, so it cleared pageFocusTo, and the followPageFocus() call after paint does nothing. In the early runs the trace shows the same jump to 'Invite people', and then followPageFocus moves focus on to the textarea. Unclaimed side note: even when it works (1.5 s, 2.5 s), the typed text lands at the start ('edit ended:  and breadGroceries'). The original gives 'Groceries and bread'.

Skeptic's fix lead: src/content/index.ts twinOf() (~311): when spot.ref is set, accept the control with the same data-ref even if its tag changed, at least a button that became an input or textarea. Then refocus keeps focus on the same page element instead of falling through to spot.near. Also, followPageFocus() (~3396) should not clear pageFocusTo when the matched ctl is not an editable field but to.el now is (isContentEditable or input/textarea). Keep it for the call after paint(). When following into a textarea that stands for a contenteditable, put the caret where the page's selection is, or at the end, so typing appends as on the original.

## F1411 (medium): HN thread: 'next' takes 1.4-2.0 s to move focus and freezes the page with 500-930 ms long tasks; the original starts scrolling in 36 ms

Found by: T4-generic. Where: news.ycombinator.com/item?id=50224463 (677 comments), the per-comment 'next' (and likely prev/parent/root) links

Evidence: Sift, 4 clicks on 'next' in 2 loads: focus reached the next top-level comment at 1461, 2014, 1403 and 1511 ms. Each click caused 3 long tasks: 584/656/619, 927/755/618, 672/562/617 and 666/662/511 ms. The target is right (fwlr at y=74, then ttul, then jstanley; /home/nico/projects/sift-test-4/research/shots/r14t4-hn-next.png). In the same tab with Sift switched off, the original's 'next' fired scroll events from 36 ms (6, 27, 62, 114… px). CPU profile of the Sift click (content.js self time): querySelectorAll 313 ms, querySelector 151, tlen 135, clean 132, threadRowsInto 64, hrefOf 61, rawText 60, findArticle 50, visitEl 48. So the click sets off about 3 full re-extractions of the thread.

Repro: With HN not rate-limiting: SIFT_PORT=<port> SIFT_TAB=<tab> bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/t4r14/hnnext4.ts (one load: Sift 'next' with focus and long-task log and profile, then the original's 'next' with Sift off, then switches Sift back on).

Suspected cause: The in-page jump (scroll and/or the page's own JS scroll) triggers the mutation, scroll or hash re-look path, and each look of a 677-comment thread costs 500-670 ms. Skipping or cheapening re-looks after an in-page jump that changes no DOM (or one reused look) would bring it near the original.

Skeptic: Confirmed, medium. I ran my own script without the profiler on 2 loads of item 50224463 (677 comments), at light load. Sift's 'next' moved focus to the right comment (fwlr, then AnotherGoodName, at y=74) at 1398, 1399 and 1220 ms. Each click caused three long tasks: 609/551/467, 519/694/623 and 607/461/593 ms. With Sift off in the same tab, the original fired scroll events from 28-36 ms and had no long tasks. One caveat the claim leaves out: the original's smooth scroll reaches the target only at about 1519 ms. So arrival time is about equal. The real harm is 1.2-1.4 s with no feedback after a click while the page is frozen, plus another ~600 ms freeze after focus lands. The cause is in the code. The link path in index.ts (about line 3485) calls afterAct(), which schedules 3 full looks at 60, 400 and 1200 ms (line ~3195). The host click listener (line 2733) adds another look. One look of this thread costs 400-750 ms (the extractor harness gave the same cost for this copy and for main). followAnchor's showPlace (150 ms timer) waits behind those looks. main's index.ts is identical.

Skeptic's fix lead: src/content/index.ts. In the link click path (about line 3485), when the link is a same-page anchor (followAnchor applies), run showPlace before any re-look. In afterAct (about line 3192), skip the fixed 60/400/1200 ms looks unless the page actually mutated (let the MutationObserver drive them), or make it one look. The host click listener at line 2733 should not add a second look on the same click.
