# Round 14 findings: perf16-findings

F14xx are new in round 14 (found while testing the round 13 build). Older ids are earlier findings a round 13 recheck found only partly fixed. Each was reproduced by a skeptic. The suspected cause and fix are leads, not orders.

## F1401 (high, regression): YouTube home and search: Sift's first list entry shows 0.8 to 1.9 s after the original's first entry (1.3x to 1.6x slower)

Found by: T1-youtube. Where: https://www.youtube.com/ and https://www.youtube.com/results?search_query=… (live, 1280x900)

Evidence: scripts/firstpaint.ts, 3 runs per side, Sift off and on in turns, medians. Home ('ytd-rich-item-renderer', --sift li.item), set 1: original 2251 ms vs Sift 3170 ms (+919). Set 2: 2922 vs 3762 (+840). Search 'rick astley' (video renderer or lockup): 2672 vs 3644 (+972). Search 'gluten free bread' ('ytd-video-renderer', STATUS.md's command): 3169 vs 5095 (+1926). Sift's 'Loading' line shows at 0.7-1.4 s. In every Sift-on run, 'original under Sift' equals Sift's time: Sift draws its list in the frame where YouTube's own first entry appears, but that frame comes about 0.9 s or more later than with Sift off. Long tasks before first content, Sift on: 7-9 (1.9-3.9 s, longest up to 2.3 s). Sift off: 5-7 (1.2-2.1 s). STATUS.md, round 12 base, same method: home +132 ms, search -180 ms. The merged build is slower. V8 trace of the search load (first 4.5-6 s): Sift's content.js takes 214-583 ms on, 63-137 ms off. Native '(program)' time is 1008-1542 ms on, 914-1476 ms off. Sift's time is spread over many functions (loadFont 34-59 ms, dialogIn/findDialog, visible, fillScreen, drawnPlaceholder, openAtPost, watchShadows, findNav). Layout and style totals are similar on and off. The watch page is not affected: title 926 vs 5047 ms; Sift's player bar 1684 ms vs the original's video element 1713 ms.

Repro: cd /home/nico/projects/sift-test-1; SIFT_PORT=9461 ./scripts/chrome.sh start; SIFT_PORT=9461 SIFT_TAB=T1-youtube bun scripts/firstpaint.ts https://www.youtube.com/ 'ytd-rich-item-renderer' 3 --sift li.item; SIFT_PORT=9461 SIFT_TAB=T1-youtube bun scripts/firstpaint.ts 'https://www.youtube.com/results?search_query=gluten+free+bread' 'ytd-video-renderer' 3 --sift li.item. Each prints medians where Sift minus original is +0.8 to +1.9 s. Profile: MODE=on (then MODE=off) SIFT_PORT=9461 SIFT_TAB=T1-youtube T=4500 bun /tmp/claude-1001/-home-nico/aac11194-acaf-4dad-a334-0620115b1898/scratchpad/t1r13/loadtrace.ts 'https://www.youtube.com/results?search_query=gluten+free+bread'

Suspected cause: Sift's load-time work on YouTube (round 12's progressive first look and sliced list drawing, plus generic helpers like findDialog, findNav and visible running on an adapter page, and font loading) competes with YouTube's own rendering on a busy main thread. YouTube's first grid or result row then paints later. Sift waits for that row, so its list is late too. The round 12 merge is the likely trigger, since round 12 base measured +132 / -180 ms.

Skeptic: Reproduced, but the gap is about half what was claimed. Severity is medium, not high. firstpaint.ts on 9461, Sift off and on in turns, medians (load average 1 to 4, other test Chromes running). Home (ytd-rich-item-renderer --sift li.item): 3 runs per side gave +56 ms, then 5 runs gave +293 and +579 ms (original 2044/2367/2473 vs Sift 2100/2660/3052). Search 'gluten free bread' (ytd-video-renderer), 5 runs per side, twice: original 2384 vs Sift 2961 (+577), and 1975 vs 2647 (+672). Search 'rick astley': 2314 vs 2845 (+531). So Sift's first list entry comes 0.3 to 0.7 s later (1.1x to 1.3x), not 0.8 to 1.9 s. In every Sift-on run, the original's first renderer appeared in the same frame as Sift's list. So YouTube's own row is delayed when Sift is on. DOMContentLoaded is also later with Sift on (search: about 1400-1730 ms on vs 970-1350 off). Sift's Loading line shows at 0.86-1.3 s, before the original's first contentful paint. V8 trace of the first 2.3 s of the search load: Sift's content.js took 127 ms with Sift on and about 3 ms with it off (loadFont 26, openAtPost 9, run 8, dialogIn 7). Over 4.5 s it took 77-191 ms on vs about 70 ms off, and those traces were noisy. Sift's JS time alone is smaller than the delay, so the exact cause is not pinned down. Regression not verified: the round 12 base numbers in STATUS.md (+132 / -180) were taken at load average 6 to 12 with wide ranges, and I did not build the base.

Skeptic's fix lead: src/content/index.ts boot/schedule: on a YouTube adapter page, before the adapter has its first entry, do not run the full extraction pass on every mutation batch. Skip generic helpers such as dialogIn/findDialog, watchShadows, openAtPost and fillScreen, and wait cheaply for the first ytd-rich-item-renderer / ytd-video-renderer instead. Defer loadFont (two woff2 fetches plus FontFace.load) until after the first list draw or to requestIdleCallback. Re-measure with firstpaint.ts, 5 runs, on home and search. Build the round 12 base to settle the regression question.

## F1407 (high): GitHub (repo, file view, issues list) and a Wikipedia article show their first content 0.3-0.5 s later than the original (1.9-2.9x)

Found by: T3-tools. Where: https://github.com/preactjs/preact, https://github.com/preactjs/preact/blob/main/hooks/src/index.js, https://github.com/preactjs/preact/issues, https://en.wikipedia.org/wiki/Bread (and, less clearly, https://www.openstreetmap.org/search?query=Coit%20Tower)

Evidence: firstpaint.ts at load average 4-6, 3 runs each side, original (Sift off) vs Sift, medians. GitHub repo ('table[aria-labelledby=folders-and-files]', --sift table): 285 vs 814 ms (off 207/285/366, on 971/814/572). GitHub file ('.react-code-text', --sift pre): 199 vs 548 ms (off 196/199/380, on 456/548/627). GitHub issues ('a[data-testid=issue-listitem-title-link]', --sift li.item): 365 vs 688 ms (off 365/296/517, on 730/688/658). Wikipedia Bread ('#firstHeading'): 207 vs 571 ms (off 216/197/207, on 571/274/575). Under load 16-25 the gaps were similar or larger: repo 541 vs 1045, issues 687 vs 1051, file 533 vs 2283, Bread 348 vs 930 ms. OSM one-result search ('#sidebar_content li', Sift 'main ul li a' with 'Coit Tower', scratchpad copy fp2.ts): 647 vs 830 ms (+183). With Sift on, DOMContentLoaded moves later (Bread 1011-1252 vs 464-552 ms). Long tasks before content are 99-330 ms with Sift on vs 0 ms off on Bread, and 187-327 vs 0-97 ms on the GitHub file. The 'Loading' line comes at 162-406 ms, so the user sees it while the original would already show its content. The works.md line 119 claim (blob code before the original's, 2453 vs 4577 ms) came from the old script and does not hold with the new one. MDN, Maps (search, place, route), OSM directions and weather.com are equal or faster.

Repro: cd /home/nico/projects/sift-test-3; SIFT_PORT=9463 ./scripts/chrome.sh start; export SIFT_PORT=9463 SIFT_TAB=T3-tools; bun scripts/firstpaint.ts https://github.com/preactjs/preact/blob/main/hooks/src/index.js .react-code-text 3 --sift pre; bun scripts/firstpaint.ts https://github.com/preactjs/preact 'table[aria-labelledby=folders-and-files]' 3 --sift table; bun scripts/firstpaint.ts https://github.com/preactjs/preact/issues 'a[data-testid=issue-listitem-title-link]' 3 --sift li.item; bun scripts/firstpaint.ts https://en.wikipedia.org/wiki/Bread '#firstHeading' 3. Run them when the machine is quiet (check uptime) and compare the medians.

Suspected cause: These pages are server-rendered, so the original paints at about 200-370 ms. Sift's content script work during parsing (first look plus render) adds 0.3-0.5 s of main-thread time before its first full view, and it pushes DOMContentLoaded back. This is the F1220/F1300 pattern on real tool pages. The round 12 120 ms first-look budget does not bring these pages within 100 ms.

Skeptic: Reproduced. Severity is medium, not high, and this is the same cause as F1300 (medium). Runs used scripts/firstpaint.ts on port 9463, tab skeptic, at load average 6-13, Sift off and on in turns. Wikipedia Bread ('#firstHeading', 5 runs a side, twice): 338 vs 430 ms, then 270 vs 580 ms. Pooled over 10 runs a side: 301 vs 578 ms, +277 ms. GitHub file ('.react-code-text', --sift pre, 5 runs, twice): 597 vs 937 ms, then 383 vs 564 ms. Pooled: 469 vs 772 ms, +303 ms. GitHub repo ('table[aria-labelledby=folders-and-files]', --sift table): 463 vs 951 ms (+488), then 827 vs 1282 ms (+455). GitHub issues list (--sift li.item): 372 vs 711 ms (+339), then 1049 vs 1782 ms (+733). Every Sift-on run was later than the Sift-off median. DOMContentLoaded moves later with Sift on: Bread 1250-2470 vs 494-931 ms. Long tasks before content: Bread 93-695 ms on vs 0-76 ms off; GitHub file 190-785 vs 0-241 ms. With Sift on, the original's own code element was often ready at 257-470 ms, while Sift's pre came at 432-1249 ms. The ratio is 1.5-2.1x, not 2.8x, but the added 0.2-0.5 s holds. Control: MDN toUpperCase 136 vs 166 ms, equal as claimed. I did not recheck OSM. A load profile with Sift on (scratchpad skn0/loadprof.ts) puts most of the time in Sift. On the GitHub blob, extract runs several times during parsing (schedule2, MutationObserver and loadedAgain), about 715 ms inclusive under the profiler. findTop takes 189 ms and leadHeadingEl 88 ms, mostly forced layout. On Bread, openAtPost (185 ms self), table fit (123 ms) and processAi (159 ms) also run before the first full view.

Skeptic's fix lead: src/content/index.ts schedule()/run(): while document.readyState is 'loading' and a first view already shows the page's main block, do not re-extract on every mutation batch; wait until DOMContentLoaded. Defer openAtPost, processAi and the table fit() pass (ui) until after the first paint, using requestIdleCallback. In generic.ts, cache findTop() (line ~6862) and leadHeadingEl per run, or skip their getBoundingClientRect calls during parsing. Track this under F1300's within-100-ms target rather than as a new high finding.

## F1220 (still open, partly; original repro in /home/nico/projects/sift/research/round12/*.md or round11/*.md)

Recheck by T6-fixtures: firstpaint.ts h1, 3 runs per side, medians. Fixed: core-budget, original 323 vs Sift 364 ms (1.1x); round 12 had about 10 s vs 2.3 s. Improved but still 2 to 4 times slower: core-buttons3000 133 vs 484 ms (3.6x, +351 ms; runs 412/484/802); core-buttonsli3000 154 vs 598 ms (3.9x, +444 ms; runs 451/598/703); core-nav3000 160 vs 323 ms (2.0x, +163 ms); core-buttons1000 208 vs 404 ms (1.9x, +196 ms). The round 12 skeptic's frame probe had buttons3000 627-894 ms, buttonsli3000 1002-1225 ms and nav3000 468-775 ms. Not slower, and noisy (page images load for 30 s): r5ext-wall3000 2260 vs 3072 ms (1.4x) and r6ext7-wallul3000 4812 vs 2414 ms (0.5x). With Sift on, core-budget's DOMContentLoaded still comes at 2.8-4.3 s, against 0.85-1.3 s off. So a freeze after first content remains, and that is extraction cost.

Skeptic: Partly fixed, confirmed at medium severity. I measured on Chrome 9466, tab skeptic, with firstpaint.ts h1. The machine was heavily loaded (load average 13 to 23 on 6 cores), so absolute times are inflated. The gap Sift adds was steady, though. core-buttons3000: original 312 vs Sift 612 ms (5 runs per side), then 380 vs 746 ms (3 runs). That is +300 to +366 ms. core-buttonsli3000: 202 vs 639 ms (+437), then 452 vs 756 ms (+304). core-nav3000: 269 vs 546 ms (+277). core-buttons1000: 272 vs 577 ms (+305). So Sift is still 1.7 to 3.2x later, adding about 0.3 to 0.45 s. Round 13's target was within about 100 ms. My core-budget run gave 242 vs 614 ms (+372). That is worse than the claim's 323 vs 364, but it is one 3-run set under load, so I do not dispute the claim's 'fixed' there. Sift on delayed DOMContentLoaded to 3.0 to 9.1 s on core-budget, against 1.0 to 1.6 s off. In one logged load, the full look after the partial view was a single 10.4 s long task (data-ms 9207). So the freeze after first content is real. Cause, from a trace and CPU profile of core-buttons3000 with Sift on: one long task of 343 to 437 ms comes right before Sift's first content. Almost all of it is Sift's own code: DOMContentLoaded handler, then loadedAgain, then run, then extract at 253 ms; paint is only 24 ms. A per-look log shows the look before DOMContentLoaded rendered only the 'Loading' line. The budgeted first look (50 ms budget) then took 210 to 317 ms and showed the list's first part (908 chars). A full look of 737 to 1023 ms followed. The 50 ms budget overruns 4 to 6x. pastDeadline() in extract/generic.ts is checked only inside the walk, after 256 elements. mainRoot, besideMain, mainCompanions, visibleMains, tlen and detectItems/controlInto all run over the whole page or the whole 3000-child grid with no deadline. These are not artifacts: Sift off has no such task, and the fixtures have no page scripts.

Skeptic's fix lead: In src/content/extract/generic.ts, make the first-look deadline cover more than the walk. Inside detectItems/controlInto, while a deadline is set, examine only the first screenful of a container's children. Bound the whole-page scans in mainRoot, besideMain, mainCompanions and visibleMains (tlen over every element), for example by checking pastDeadline or capping the scanned elements while deadline < Infinity. In src/content/index.ts run(), the first look before DOMContentLoaded rendered only the Loading line; the content was not shown until the next look, after DOMContentLoaded. Either let that look (budget 50) render the partial content it reads, or bring the next one forward. For core-budget's after-first-view freeze, the full look (budget 0) should be split across tasks or kept away from the DOMContentLoaded task. loadedAgain currently runs it synchronously there, which freezes the view for seconds.
